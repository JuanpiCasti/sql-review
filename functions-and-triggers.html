Functions & triggers, or, code that lives in the database

Logic the database executes on your behalf — a tiny imperative language inside a declarative one, plus the hooks that fire automatically when a row changes.

Stored logic is contentious — pushed too far it becomes a parallel application no one reviews, but used judiciously it gives you transactional consistency that no application-layer code can match. This chapter is the shape of the tool, not a recommendation about how much of it to use.

Functions & triggers, in one card

CREATE FUNCTION
Returns a value (scalar, set, table). Cannot manage transactions.
CREATE PROCEDURE
No return. Can COMMIT / ROLLBACK mid-body. Called with CALL.
LANGUAGE sql
Pure SQL body. Inlinable by the planner — preferable when it fits.
LANGUAGE plpgsql
Loops, conditionals, exceptions. Opaque to the planner.
IMMUTABLE
Same inputs → same output, always. Indexable in expression indexes.
STABLE
Constant within a single statement. Safe as an index predicate filter.
VOLATILE
Default. May return different values, may have side effects.
BEFORE trigger
Can modify NEW. Return NULL to skip the row.
AFTER trigger
Row is already written. Right place for audit logs.
SECURITY DEFINER
Runs as the function's owner. Always pin search_path.
