Functions & triggers, or, code that lives in the database

Logic the database executes on your behalf — a tiny imperative language inside a declarative one, plus the hooks that fire automatically when a row changes.

Stored logic is contentious — pushed too far it becomes a parallel application no one reviews, but used judiciously it gives you transactional consistency that no application-layer code can match. This chapter is the shape of the tool, not a recommendation about how much of it to use.

LANGUAGE sql vs plpgsql

Postgres supports several procedural languages, but two cover almost every real use case. LANGUAGE sql functions have a body made entirely of one or more SQL statements; LANGUAGE plpgsql functions add control flow — IF, LOOP, BEGIN … EXCEPTION, variables, RAISE. Pick the smallest tool that fits.

The crucial property of a sql function is that the planner can inline it: if the body is a single SELECT and the function is not SECURITY DEFINER, calls to it are textually substituted into the calling query before planning. Indexes on the underlying columns still apply, the planner sees the whole picture, and the function call disappears from the plan tree. A plpgsql function is a black box — the planner cannot see through it, statistics do not propagate, and every call is a separate plan invocation.

A trivially inlinable function

CREATE FUNCTION account_balance(p_id bigint) RETURNS numeric
  LANGUAGE sql STABLE AS $$
    SELECT coalesce(sum(amount), 0) FROM ledger WHERE account_id = p_id
$$;

-- The planner inlines this; the index on ledger(account_id) is used.
SELECT id, account_balance(id) FROM accounts WHERE active;

Once you need a loop, an exception handler, or an intermediate variable, plpgsql is the answer. The price is opacity — write the function as small as it will go, and keep the heavy lifting in pure SQL inside it.

When plpgsql earns its keep

CREATE FUNCTION upsert_user(p_email text, p_name text)
RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE
  v_id bigint;
BEGIN
  INSERT INTO users (email, name) VALUES (p_email, p_name)
    ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name
    RETURNING id INTO v_id;
  RETURN v_id;
EXCEPTION WHEN unique_violation THEN
  -- a concurrent insert beat us; re-read the row.
  SELECT id INTO v_id FROM users WHERE email = p_email;
  RETURN v_id;
END $$;
Other languages LANGUAGE plpython3u, plperlu, plv8, and friends exist. They are powerful, "untrusted" (the u), and almost never the right choice when the alternative is a few more lines of pure SQL. Reach for them only when you genuinely need a library that has no equivalent inside the database.

Volatility — IMMUTABLE, STABLE, VOLATILE

Every function carries a volatility label that promises something about its behaviour. The planner uses that promise to decide when it is safe to cache results, push the function through index expressions, or evaluate it only once per query. Getting the label wrong does not crash anything — it produces wrong answers, silently.

IMMUTABLE
Same inputs always produce the same output, with no side effects and no dependency on database state. Pure mathematics. The planner can evaluate the function once at plan time, and the result may appear in an expression index.
STABLE
Within a single statement, the function will return the same output for the same inputs. May read tables. Safe to use in an index predicate and as the constant side of an index lookup, but not in an expression index.
VOLATILE
The default. May return different values on successive calls with the same arguments (random(), nextval()) or have side effects (INSERT inside). Must be evaluated row-by-row.

The classic mistake is labelling a function IMMUTABLE because the body is "pure SQL," forgetting that a SELECT against another table is not immutable — the data can change. The planner takes the promise at face value, caches the result, and now the function returns last week's answer.

The exact shape of the bug

-- WRONG: reads a table, claims immutability.
CREATE FUNCTION current_rate() RETURNS numeric
  LANGUAGE sql IMMUTABLE AS $$ SELECT rate FROM fx WHERE pair = 'USD/EUR' $$;

-- An expression index against this is allowed but lies:
CREATE INDEX … ON invoices ((amount * current_rate()));
-- Index entries are frozen at insert time. Updating fx does not refresh them.

The right labels in practice: IMMUTABLE for genuinely pure helpers (string manipulation, arithmetic, date math that does not touch now()); STABLE for "reads tables but doesn't write"; VOLATILE for everything else, including anything that calls random(), reads now(), or writes. now() itself is STABLE — it returns the start of the current transaction, not wall-clock time.

Pitfall

PARALLEL SAFE / PARALLEL RESTRICTED / PARALLEL UNSAFE is a related but separate label, controlling whether a function can run inside a parallel worker. The default is PARALLEL UNSAFE, which silently disables parallel plans for any query that calls the function. Pure helpers should be marked PARALLEL SAFE explicitly.

Procedures and embedded COMMIT

The thing that makes a procedure different from a function is that it can commit. Functions run inside the caller's transaction and have no way to influence it; a procedure called with CALL can issue COMMIT and ROLLBACK mid-body. That single capability is what makes procedures useful — without it they would be functions with a stranger return convention.

The use case is large batch jobs that should not run as one enormous transaction: archiving, backfills, queue draining. A function would have to do the whole thing in one transaction and hold its locks the entire time; a procedure can commit every few thousand rows.

Chunked archive, committing per batch

CREATE PROCEDURE archive_old_orders(p_cutoff timestamptz)
LANGUAGE plpgsql AS $$
DECLARE
  v_moved integer;
BEGIN
  LOOP
    WITH chunk AS (
      DELETE FROM orders
      WHERE  created_at < p_cutoff
      RETURNING *
      LIMIT 5000
    )
    INSERT INTO orders_archive SELECT * FROM chunk;

    GET DIAGNOSTICS v_moved = ROW_COUNT;
    EXIT WHEN v_moved = 0;

    COMMIT;                          -- release locks, free up WAL, breathe
  END LOOP;
END $$;

CALL archive_old_orders('2024-01-01');
Note

You cannot CALL a procedure that contains COMMIT from inside an open transaction, because that COMMIT would close the caller's transaction unexpectedly. Procedures with embedded transaction control must be called from a statement that itself runs outside BEGIN … COMMIT — and most migration tools need a "non-transactional" flag on the step.

Procedures have no return value (RETURNS is not part of the syntax). Output is via INOUT parameters, which the CALL statement returns as a one-row result set.

Triggers — BEFORE, AFTER, INSTEAD OF

A trigger is a function bound to a table (or view) that Postgres fires automatically when a row event happens. The function takes no arguments — it reads NEW and OLD from the implicit per-row context — and returns either a row (for BEFORE and INSTEAD OF) or nothing meaningful (for AFTER).

The timing keyword decides everything about what the trigger can do:

BEFORE
Fires before the row is written. Can modify NEW to rewrite the row that is about to be inserted or updated. Returning NULL aborts the operation for this row — no error, no write, the surrounding UPDATE just reports one fewer row affected.
AFTER
Fires after the row is written, and after any BEFORE trigger's transformations. Cannot change the row. The right place for audit logs, foreign-key cascades, derived-data updates, anything that must observe the post-write state.
INSTEAD OF
Only valid on views. The trigger function replaces the would-be operation on the view — it is how you make a non-trivial view writable. INSERT on the view fires the trigger, which translates it into INSERTs on the underlying tables.

A BEFORE trigger that timestamps and normalises

CREATE FUNCTION set_updated_at() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();
  NEW.email      := lower(NEW.email);
  RETURN NEW;
END $$;

CREATE TRIGGER users_touch
  BEFORE UPDATE ON users
  FOR EACH ROW
  EXECUTE FUNCTION set_updated_at();

An AFTER trigger that audits

CREATE FUNCTION audit_users() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO users_audit (op, user_id, at, before, after)
  VALUES (TG_OP, coalesce(NEW.id, OLD.id), now(), to_jsonb(OLD), to_jsonb(NEW));
  RETURN NULL;                       -- AFTER triggers ignore the return value
END $$;

CREATE TRIGGER users_audit_t
  AFTER INSERT OR UPDATE OR DELETE ON users
  FOR EACH ROW EXECUTE FUNCTION audit_users();

The implicit context variables — TG_OP ('INSERT' / 'UPDATE' / 'DELETE'), TG_TABLE_NAME, TG_WHEN, TG_LEVEL — let one function serve multiple triggers when the shape is similar enough.

Statement-level vs row-level triggers

The FOR EACH ROW qualifier on the examples above is one of two options. The other is FOR EACH STATEMENT, and the choice has performance consequences that grow linearly with the size of the operation.

A row-level trigger fires once per affected row. A statement-level trigger fires once per statement, regardless of how many rows it touched. For a bulk UPDATE that hits a million rows, the row-level audit trigger from the previous section fires a million times — a million plpgsql invocations, a million INSERTs. The statement-level equivalent fires once.

The catch is that statement-level triggers historically had no visibility into the rows. PG 10 fixed that with transition tables — declared with REFERENCING NEW TABLE AS … / OLD TABLE AS … — which expose the entire set of affected rows as a virtual table the trigger function can query.

A statement-level audit, set-based

CREATE FUNCTION audit_users_set() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO users_audit (op, user_id, at, before, after)
  SELECT TG_OP,
         coalesce(n.id, o.id),
         now(),
         to_jsonb(o),
         to_jsonb(n)
  FROM   new_rows n
  FULL JOIN old_rows o USING (id);
  RETURN NULL;
END $$;

CREATE TRIGGER users_audit_set
  AFTER UPDATE ON users
  REFERENCING NEW TABLE AS new_rows
              OLD TABLE AS old_rows
  FOR EACH STATEMENT
  EXECUTE FUNCTION audit_users_set();

On a million-row update, the row-level audit can be tens of seconds of pure trigger overhead. The set-based statement-level version is a single INSERT … SELECT the planner can optimise. Default to row-level when there are fewer than a few thousand rows per statement and to statement-level with transition tables when bulk operations are routine.

Per-column AFTER UPDATE OF col1, col2 restricts the trigger to fire only when one of the listed columns changed. Cheap and worth doing on tables where most updates don't touch the columns the trigger cares about.

SECURITY DEFINER and search_path

By default a function runs with the privileges of the caller — SECURITY INVOKER. Marking it SECURITY DEFINER instead makes it run as the user who created it. That is how you let a low-privilege application user perform a tightly scoped operation that touches tables they cannot otherwise read or write — the database equivalent of a setuid binary.

And, as with setuid, the footgun lies in $PATH. The function's search_path at execution time decides which schema each unqualified table name resolves to. If the caller can influence search_path before the call, they can drop a malicious table into a schema they own that shadows one of the function's referenced tables, and the function — running as its owner — will happily read or write the attacker's version.

Security warning

Every SECURITY DEFINER function must pin its search_path, and the canonical pin is the system schema first plus whatever your application needs. Without this, you are one cleverly named public.orders table away from a privilege escalation.

The right shape for SECURITY DEFINER

CREATE FUNCTION refund_order(p_id bigint) RETURNS void
  LANGUAGE plpgsql
  SECURITY DEFINER
  SET search_path = pg_catalog, app, public        -- pinned, attacker-proof
AS $$
BEGIN
  UPDATE orders SET status = 'refunded' WHERE id = p_id;
  INSERT INTO ledger (order_id, amount) VALUES (p_id, ...);
END $$;

-- Grant the privilege carefully.
REVOKE ALL ON FUNCTION refund_order(bigint) FROM PUBLIC;
GRANT  EXECUTE ON FUNCTION refund_order(bigint) TO app_user;

A second discipline that pairs with the search_path pin: schema-qualify every reference inside the function (app.orders, not orders) when you can. The pin protects against table-shadowing; the qualification documents the intent. Together they remove the entire class of bug.

Audit existing definer functions with a quick catalog query:

Finding SECURITY DEFINER functions that have not pinned search_path

SELECT n.nspname, p.proname, p.proconfig
FROM   pg_proc p
JOIN   pg_namespace n ON n.oid = p.pronamespace
WHERE  p.prosecdef
  AND  (p.proconfig IS NULL
        OR NOT EXISTS (
          SELECT 1 FROM unnest(p.proconfig) c WHERE c LIKE 'search_path=%'
        ));

Functions & triggers, in one card

CREATE FUNCTION
Returns a value (scalar, set, table). Cannot manage transactions.
CREATE PROCEDURE
No return. Can COMMIT / ROLLBACK mid-body. Called with CALL.
LANGUAGE sql
Pure SQL body. Inlinable by the planner — preferable when it fits.
LANGUAGE plpgsql
Loops, conditionals, exceptions. Opaque to the planner.
IMMUTABLE
Same inputs → same output, always. Indexable in expression indexes.
STABLE
Constant within a single statement. Safe as an index predicate filter.
VOLATILE
Default. May return different values, may have side effects.
BEFORE trigger
Can modify NEW. Return NULL to skip the row.
AFTER trigger
Row is already written. Right place for audit logs.
SECURITY DEFINER
Runs as the function's owner. Always pin search_path.
