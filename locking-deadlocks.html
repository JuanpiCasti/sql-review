Locks & deadlocks, or, who's waiting on whom

Eight table-lock modes, four row-lock modes, one deadlock detector. The mechanics behind every blocked session and every 40P01 error in production.

MVCC means most readers don't lock and most writers don't block readers — but locks are still everywhere. They protect the structure of relations from concurrent DDL, serialise conflicting writes on the same row, and let you carve out application-defined critical sections with no schema at all. Knowing which lock mode each command takes, which conflict with which, and how the deadlock detector resolves the inevitable cycles is the difference between a database under control and one whose production logs scroll past too fast to read.

Eight table-lock modes

Every statement that touches a table takes a table-level lock in one of eight modes. The modes form a hierarchy from weakest (held by everyone, conflicts with nothing but DDL) to strongest (held alone, conflicts with everything).

ACCESS SHARE
Taken by SELECT. Conflicts only with ACCESS EXCLUSIVE.
ROW SHARE
Taken by SELECT … FOR UPDATE / FOR SHARE.
ROW EXCLUSIVE
Taken by INSERT, UPDATE, DELETE, MERGE.
SHARE UPDATE EXCLUSIVE
Taken by VACUUM (non-FULL), ANALYZE, CREATE INDEX CONCURRENTLY, some ALTER TABLE.
SHARE
Taken by CREATE INDEX (non-concurrent).
SHARE ROW EXCLUSIVE
Taken by some ALTER TABLE forms.
EXCLUSIVE
Taken by REFRESH MATERIALIZED VIEW CONCURRENTLY.
ACCESS EXCLUSIVE
Taken by DROP TABLE, TRUNCATE, VACUUM FULL, most ALTER TABLE, CLUSTER. Conflicts with everything — even SELECT.
Why the names "Share" / "Exclusive" describe whether the lock can be co-held with others of the same mode. "Row" in the name means "I will modify rows" — these modes don't conflict with each other because row-level concurrency is handled by row locks, not the table lock.

The DDL trap

Most ALTER TABLE forms take ACCESS EXCLUSIVE, which conflicts with SELECT. If a long-running query is reading the table when your migration runs, the migration blocks behind it — and every new SELECT queues behind the migration. A 30-second analytic query plus a one-millisecond ALTER TABLE can stall your entire application for 30 seconds. Set lock_timeout = '2s' on migrations.

Four row-lock modes

Inside a table, individual rows can be locked by SELECT. There are four row-lock strengths, from weakest to strongest:

FOR KEY SHARE
Prevents other transactions from changing the row's key columns or deleting it. Held implicitly by foreign-key checks on the parent side.
FOR SHARE
Prevents any update or delete; multiple sessions can hold it.
FOR NO KEY UPDATE
Same as FOR UPDATE but doesn't block FOR KEY SHARE. Taken implicitly by UPDATE on non-key columns.
FOR UPDATE
Strongest. Prevents any other lock; the row is yours to modify.

The two weaker modes exist because of foreign keys. An INSERT into a child table needs to verify the parent row exists, but should not block parallel updates to non-key columns of that parent. The KEY-aware modes carve out exactly that gap.

Pessimistic locking with FOR UPDATE

BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- any concurrent UPDATE / DELETE / SELECT FOR UPDATE on this row blocks here

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

NOWAIT and SKIP LOCKED

By default, locking SELECTs wait. Two modifiers change that:

NOWAIT
Raise ERROR: could not obtain lock on row immediately if the row is locked.
SKIP LOCKED
Silently omit locked rows from the result set.

SKIP LOCKED is the trick that lets you build a low-contention work queue inside a Postgres table — no Redis, no SQS, just a table and a query:

A work queue in nine lines

-- N workers run this in a loop, in parallel
BEGIN;
SELECT id, payload
FROM jobs
WHERE state = 'pending'
ORDER BY priority, id
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- ... do the work ...

UPDATE jobs SET state = 'done' WHERE id = $1;
COMMIT;

Each worker grabs a different row because the rows the others already hold are skipped. No worker ever waits. The hot pages do see contention, but the rows themselves don't.

Deadlocks

A deadlock is a cycle: A holds X and wants Y; B holds Y and wants X. Both sit forever. Postgres detects this with a background check that runs deadlock_timeout (default 1s) after any session starts waiting on a lock. If a cycle is found, Postgres picks one transaction as victim and aborts it with SQLSTATE 40P01:

t
Session A
Session B
t1
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
t2
UPDATE accounts SET balance = balance + 50 WHERE id = 2;
-- waits for B
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
-- waits for A — cycle
t3
After deadlock_timeout, Postgres aborts one of them:
ERROR: deadlock detected (SQLSTATE 40P01)

The prevention is mechanical: always acquire locks in a consistent order. If both transactions had touched id=1 before id=2, there would be no cycle — one would wait for the other and complete normally.

The retry contract

Like serialization failures, 40P01 is a normal, expected outcome under contention. Your application must catch it and retry the entire transaction — not the failing statement. Most ORMs offer a retry decorator for exactly this.

Inspecting locks

The system view pg_locks shows every lock currently held or waiting in the cluster. Joined to pg_stat_activity, it becomes the answer to "what is blocking what?":

Who is blocking whom

SELECT blocked.pid     AS blocked_pid,
       blocked.query   AS blocked_query,
       blocking.pid    AS blocking_pid,
       blocking.query  AS blocking_query,
       blocking.state  AS blocking_state,
       now() - blocked.xact_start AS blocked_for
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE NOT blocked.wait_event_type IS NULL;

SELECT pg_terminate_backend(21887); -- closes the connection entirely

Advisory locks

Sometimes you need mutual exclusion that has nothing to do with rows — running a singleton cron job, serialising a leader-election protocol, gating a cache rebuild. Advisory locks are application-defined locks identified by one or two arbitrary integers, with no relation to any table.

A singleton cron lock

-- one worker grabs it; the others find it taken and exit
SELECT pg_try_advisory_lock(42) AS got_it;

-- session-scoped: released on disconnect or pg_advisory_unlock(42)
-- transaction-scoped variant releases at COMMIT/ROLLBACK:
SELECT pg_advisory_xact_lock(42);
pg_advisory_lock(n)
Wait until acquired; session-scoped.
pg_try_advisory_lock(n)
Non-blocking; returns boolean.
pg_advisory_xact_lock(n)
Wait; auto-released at end of transaction.
pg_advisory_unlock(n)
Release a session-scoped lock.

Advisory locks live in the same shared lock table as everything else and show up in pg_locks with locktype = 'advisory'.

Locks, in one card

ACCESS EXCLUSIVE
Blocks everything, including SELECT. Held by most DDL.
ROW EXCLUSIVE
Held by every INSERT / UPDATE / DELETE.
SELECT FOR UPDATE
Pessimistic row lock; blocks other writers of that row.
FOR UPDATE SKIP LOCKED
Build queues without contention.
NOWAIT
Don't wait; raise an error if locked.
deadlock_timeout
Default 1s. Time before deadlock detector runs.
40P01
Deadlock victim error. Always retry the whole transaction.
lock_timeout
Per-session cap on how long any single lock wait can take. Set on migrations.
pg_blocking_pids(pid)
Array of PIDs blocking the given PID. The blocker query earlier in this chapter is built on it.
Advisory locks
Application-defined mutexes. Session- or transaction-scoped.
