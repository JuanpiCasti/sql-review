EXPLAIN & the planner

Postgres turns your declarative SQL into an imperative plan. Reading that plan — and noticing when the planner has guessed wrong — is the single most useful debugging skill in the database.

The planner enumerates possible execution strategies for your query, estimates each one's cost using table statistics, and picks the cheapest. EXPLAIN prints the plan it chose; EXPLAIN ANALYZE runs the plan and prints what actually happened. Comparing the estimate to the reality is how you find every slow query that has ever been slow.

The two commands

EXPLAIN q
Print the planned tree with estimated costs. No execution.
EXPLAIN ANALYZE q
Run q and print actual row counts, timings, and loops alongside the estimates.
EXPLAIN (BUFFERS) q
Add per-node shared/local buffer hit/read counts. Use with ANALYZE.
EXPLAIN (FORMAT JSON) q
Machine-readable output for visualisers like depesz.com or dalibo.com.
EXPLAIN (SETTINGS) q
Show non-default GUCs in effect. Useful when a query behaves differently in production.

Defensive recipe: use this every time.

EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, FORMAT TEXT) <your query>;
Caveat

EXPLAIN ANALYZE actually executes the query, including any UPDATE, DELETE, or INSERT it contains. To inspect a mutation safely, wrap it in a transaction and roll back:

BEGIN;
EXPLAIN (ANALYZE, BUFFERS) DELETE FROM events WHERE created_at < '2020-01-01';
ROLLBACK;

Reading the output

A small example:

A simple plan, annotated

EXPLAIN ANALYZE
SELECT c.name, sum(o.total)
FROM   customers c
JOIN   orders    o ON o.customer_id = c.id
WHERE  o.placed_at >= now() - interval '30 days'
GROUP  BY c.id;

Output

                 (actual time=185.2..186.1 rows=1198 loops=1)
  Group Key: c.id

                  (actual time=2.1..172.4 rows=110340 loops=1)
       Hash Cond: (o.customer_id = c.id)
       -> Index Scan using orders_placed_at_idx on orders o

            Index Cond: (placed_at >= (now() - '30 days'::interval))

Planning Time: 0.412 ms
Execution Time: 186.7 ms

How to read it:

  • Plans are trees, printed depth-first, deepest node innermost. The top line is the final operation.
  • Each node prints cost=startup..total rows=estimated width=bytes and (with ANALYZE) actual time=startup..total rows=actual loops=n.
  • Cost is in abstract units — one unit ≈ the cost of reading one sequential page. It is not seconds.
  • Loops means "how many times this subtree ran." For nested loops, the inner node's totals are per loop; multiply by loops for total work.
  • The most diagnostic line is the discrepancy between estimated rows and actual rows. Order-of-magnitude misestimates are why most plans go wrong.

Plan nodes you'll see all the time

Scans

Seq Scan
Read every page of the table. Correct for small tables or for queries returning a large fraction of rows.
Index Scan
Walk an index, then fetch each row from the heap. Best for selective queries (few rows).
Index Only Scan
Walk the index without touching the heap. Requires every selected column to be in the index, and pages marked all-visible.
Bitmap Index Scan + Bitmap Heap Scan
Build a bitmap of matching tuple IDs from one or more indexes, then fetch them in heap order. Cheap for medium selectivity; combines multiple indexes via BitmapAnd / BitmapOr.

Joins

Nested Loop
For each outer row, probe the inner side. Excellent when the outer is tiny and the inner has a usable index. Disastrous when the outer is large.
Hash Join
Build a hash table over the smaller side, probe it with the larger. Works only for equi-joins. The default for medium/large joins when memory allows.
Merge Join
Both inputs sorted by the join key; walk them in lockstep. Useful when both sides arrive pre-sorted (e.g. from index scans on the join key).

Aggregation, sort, limit

HashAggregate
Group by hashing the group key. Default when memory allows.
GroupAggregate
Group by walking already-sorted input. Picked when input is pre-sorted (often after an index scan).
Sort
Spool, sort, emit. Note the Sort Method line: quicksort Memory: … is fine, external merge Disk: … means you blew past work_mem.
Limit
Stop pulling rows after N. Crucial for early termination in nested-loop top-N plans.
Gather / Gather Merge
Parallel-query coordinator. Children prefixed Parallel ran in worker processes.

The cost model

Each plan node has a cost formula. The numbers come from a handful of GUCs:

seq_page_cost
Cost of one sequentially-read page. 1.0, the unit.
random_page_cost
Cost of one randomly-read page. Default 4.0; on SSDs, lower this to 1.1–1.5.
cpu_tuple_cost
Per-row CPU. Default 0.01.
cpu_index_tuple_cost
Per-index-row CPU. Default 0.005.
cpu_operator_cost
Per-operator CPU. Default 0.0025.
work_mem
Memory per sort / hash node. Spills to disk above this.
effective_cache_size
The planner's estimate of how much of the data is hot in OS cache. Higher → more inclined to use indexes.

The default random_page_cost = 4 dates from the spinning-disk era. On modern SSDs it makes the planner avoid indexes for queries it shouldn't. Setting random_page_cost = 1.1 in postgresql.conf is one of the highest-impact one-line config changes you can make.

Statistics — why the planner is sometimes wrong

The planner estimates "how many rows match this predicate" using statistics gathered by ANALYZE (and run automatically by autovacuum): per-column most-common-values, histograms, null fractions, and average row width. The view pg_stats exposes them.

Things that defeat default statistics:

  • Correlated columns. Postgres assumes independent column distributions. WHERE country='US' AND zip='90210' is estimated as the product of two selectivities — but zip determines country. Fix with extended statistics: 
    CREATE STATISTICS address_corr (dependencies, ndistinct)
  ON country, zip FROM addresses;
ANALYZE addresses;
  • Skewed columns with rare values. If a value is rarer than the MCV-list threshold, the planner falls back to (1 - sum(mcv_freqs)) / n_distinct — usually a big overestimate. Raise default_statistics_target for the column with ALTER TABLE … ALTER COLUMN … SET STATISTICS 1000; and re-ANALYZE.
  • Stale stats. After a bulk load or schema change, run ANALYZE manually; don't wait for autovacuum.

Smells, in order of importance

  1. Estimated vs actual rows off by > 10×. The planner is choosing the wrong strategy because its inputs are wrong. Fix stats first; don't waste time tuning indexes against bad estimates.
  2. Sort Method: external merge Disk: … Your sort spilled. Raise work_mem for the session or add an index to avoid the sort.
  3. Seq Scan on a big table for a selective query. Missing index, or planner thinks the index isn't worth it (often: stale random_page_cost).
  4. Nested Loop with high loops count and per-loop work. Multiply actual time × loops for the inner; if it dominates, force a hash join with a higher row estimate (fix stats) or rewrite.
  5. Rows Removed by Filter: large. Postgres pulled millions of rows from a scan, then threw most of them away. Pushdown the predicate via a better-matching index or a partial index.
  6. BUFFERS: read >> hit on a frequently-run query. The data isn't in cache and every run pays full I/O. Either the table is too big for shared_buffers, or the query touches too many pages — usually back to the index discussion.

Forcing the planner's hand

Postgres has no query hints. The intentional design is that you fix the underlying problem — bad stats, missing index, mis-tuned cost GUC — rather than override the optimiser per query. But when you really must, the toolbox:

SET LOCAL enable_seqscan = off
Per-transaction. Discourages but does not forbid seq scans (costs become very high).
SET LOCAL enable_nestloop = off
Same for nested loops.
SET LOCAL work_mem = '256MB'
For one transaction; useful for a single big ad-hoc analytic query.
Materialise with a CTE
A WITH x AS MATERIALIZED (…) forces evaluation of x first, which can break a bad join order.
OFFSET 0 in a subquery
An old trick that prevents subquery flattening. The pg_hint_plan extension is the principled alternative.

EXPLAIN, in one card

EXPLAIN ANALYZE
Always include BUFFERS. Wrap mutating queries in BEGIN/ROLLBACK.
cost vs actual time
Cost is unitless. Look at actual time and rows.
rows × loops
For nested loops, multiply to get true work done in the inner side.
Seq Scan
Fine for small tables or unselective queries. Suspicious otherwise.
Bitmap scans
Postgres combining multiple indexes. Often a sign you could use a single composite index.
Hash / Merge / Nested Loop
Hash for medium/large equi-joins, Nested Loop for small outer + indexed inner, Merge when inputs already sorted.
Sort spilled to disk
Raise work_mem or add an index that delivers pre-sorted rows.
random_page_cost
Default 4 is wrong on SSDs. Set 1.1 globally.
CREATE STATISTICS
Fix correlated-column estimates.
Estimate > 10× off
The most common root cause of bad plans. Fix the stats before tuning anything else.
