Configuration & tuning, or, the dials that matter

A few hundred GUCs, of which maybe a dozen actually move performance on a given workload. This chapter is the shortlist.

Default postgresql.conf is shipped conservative — it assumes a laptop, not a server. The first time a Postgres install is put on real hardware, the dial-turning that gets it from "fine" to "fast" is almost always the same handful of settings. This chapter names them and explains what each one controls.

The GUC system — pg_settings, scope, reload

Every tunable in Postgres is a GUC — "grand unified configuration" — and every GUC is exposed through the same view, pg_settings. The view tells you the current value, the unit, the default, the source the value was loaded from, and — most importantly — the context, which says what it takes to change the setting.

Inspecting a GUC

SELECT name, setting, unit, context, source
FROM   pg_settings
WHERE  name IN ('shared_buffers','work_mem','max_connections');

Result

The five context values are worth committing to memory: internal (compile-time, untouchable), postmaster (server restart required), sighup (reloadable with SELECT pg_reload_conf()), backend (set per new connection), and superuser / user (changeable in a live session). Anything labelled postmaster is the kind of change you schedule a maintenance window for; anything sighup can be rolled out without dropping a connection.

Settings live in a tiered cascade: postgresql.conf at the bottom, then postgresql.auto.conf (written by ALTER SYSTEM), then per-database (ALTER DATABASE app SET …), per-role (ALTER ROLE etl SET …), and finally per-session (SET …) and per-transaction (SET LOCAL …). The narrower scope always wins.

Changing a GUC for real

-- Persist a value to postgresql.auto.conf.
ALTER SYSTEM SET work_mem = '32MB';

-- Reload reloadable settings without a restart.
SELECT pg_reload_conf();

-- Override for one session.
SET work_mem = '128MB';

-- Override only for the current transaction.
BEGIN;
SET LOCAL work_mem = '512MB';
SELECT … FROM big_table ORDER BY …;
COMMIT;
Don't hand-edit Never edit postgresql.auto.conf directly. It carries a "do not edit" banner and any change goes through ALTER SYSTEM. Plain postgresql.conf is fair game.

Memory — shared_buffers, work_mem, maintenance_work_mem

Three settings carve up Postgres's memory budget. They do not overlap, and the right values are functions of the hardware, not the workload — which is why the same starting points apply almost everywhere.

shared_buffers is the single shared cache of disk pages that all backends read from and write into. Past a working-set-sized cache, more buffers help less than you would hope, because the OS page cache underneath is also caching the same data. The canonical starting point is ~25% of RAM; bumping past 40% rarely repays the cost.

work_mem is per-operation: every sort, hash, and hash-join node in a plan gets its own work_mem. A single complex query can use multiples of the limit, and a hundred concurrent connections each running such a query can use a hundred times. The default of 4 MB is conservative because of exactly that multiplier. Raise it cautiously, and prefer raising it per-statement with SET LOCAL for the heavy reporting queries that actually need it.

When you can hear the spill

EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, sum(amount) FROM orders GROUP BY customer_id;

                                  QUERY PLAN
-----------------------------------------------------------------------------
 HashAggregate  (cost=18933.0..19042.4 rows=10940 width=12)
   Group Key: customer_id
   Batches: 17  Memory Usage: 4145kB  Disk Usage: 21240kB
   ->  Seq Scan on orders  (cost=0.00..14211.0 rows=944600 width=12)

"Disk Usage" in a hash aggregate or sort node means work_mem was too small and the operator spilled to a temp file. Raise work_mem until that line disappears.

maintenance_work_mem is the same idea for one-shot maintenance operations: VACUUM, CREATE INDEX, ALTER TABLE … ADD COLUMN. Because there are only a few of these running at a time, you can be generous — 512 MB to 2 GB is normal. autovacuum_work_mem falls back to this value and is the knob to use if you want autovacuum workers to be more frugal than ad-hoc VACUUM.

effective_cache_size is the odd one out — it allocates nothing. It is a hint to the planner about how much of the data is likely cached (counting both Postgres and the OS), used to estimate the cost of repeated index lookups. Set it to ~50–75% of RAM and move on.

WAL — wal_buffers, checkpoint_timeout, max_wal_size

A checkpoint is the moment Postgres guarantees that every dirty buffer up to a particular WAL position has been flushed to the heap. It is the safe restart point after a crash: recovery reads WAL from the last checkpoint and replays forward. Frequent checkpoints mean short recovery; infrequent checkpoints mean less I/O, because pages dirtied many times between checkpoints only get flushed once.

Two settings decide how often a checkpoint fires. checkpoint_timeout sets a wall-clock interval (default five minutes, often raised to fifteen or thirty). max_wal_size sets a volume cap (default 1 GB; on write-heavy workloads, raising it to several gigabytes lets the timeout win, which is what you want). Whichever threshold trips first ends the cycle.

A sensible write-heavy baseline

ALTER SYSTEM SET checkpoint_timeout      = '30min';
ALTER SYSTEM SET max_wal_size             = '8GB';
ALTER SYSTEM SET checkpoint_completion_target = 0.9;   -- spread the flush
SELECT pg_reload_conf();

checkpoint_completion_target spreads the dirty-buffer flush over a fraction of the interval (0.9 by default in recent versions). Without it, every checkpoint would be a brief, painful I/O spike at the boundary.

wal_buffers is the in-memory staging area for WAL records before they hit disk. Auto-tuned to shared_buffers / 32; rarely needs adjustment unless you see wait_event = WALWriteLock contention in pg_stat_activity.

Note

The trade-off is straightforward: longer intervals reduce average write amplification but lengthen crash recovery. If your RTO is "a few seconds," keep checkpoints frequent. If your RTO is "a minute" and your write volume is heavy, stretch them out. pg_stat_bgwriter tells you the rate at which checkpoints are firing and whether they're triggered by time or by volume (checkpoints_timed vs checkpoints_req) — you want time-triggered to dominate.

Autovacuum tuning

Autovacuum runs in the background, finding tables that have accumulated enough dead tuples or enough INSERTs since the last ANALYZE and processing them. The defaults are calibrated for a small database; on any non-trivial table they let bloat snowball before the first vacuum even fires.

The trigger is per-table and roughly: vacuum when n_dead_tup exceeds autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × n_live_tup. With the default scale factor of 0.2, a 100-million-row table sits at twenty million dead tuples before the worker even notices. That is too much.

The right adjustment is per-table, not global, and lives in the table's storage parameters:

A hot table that needs aggressive vacuuming

ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor  = 0.02,    -- 2% instead of 20%
  autovacuum_vacuum_threshold     = 10000,
  autovacuum_analyze_scale_factor = 0.01,
  autovacuum_vacuum_cost_limit    = 2000     -- let the worker do more per round
);

To know whether the workers are keeping up, watch pg_stat_user_tables:

Worst-bloated tables in the cluster

SELECT relname,
       n_live_tup, n_dead_tup,
       round(n_dead_tup::numeric / nullif(n_live_tup, 0), 3) AS dead_ratio,
       last_autovacuum
FROM   pg_stat_user_tables
ORDER  BY dead_ratio DESC NULLS LAST
LIMIT  10;

Operational warning

Autovacuum cannot reclaim dead tuples newer than the oldest open transaction in the cluster — the xmin horizon. A single long-running transaction (a forgotten BEGIN, a stuck replication slot, a sloppy ETL job) will block every worker from doing useful work, and n_dead_tup will climb regardless of how aggressive your settings are. Check pg_stat_activity and pg_replication_slots before changing autovacuum parameters.

Connections, max_connections, and pooling

Every Postgres connection is a real OS process — a postmaster fork with several megabytes of private memory, a snapshot, a transaction state. They are not lightweight. The cost is paid even for idle connections, and the contention on internal locks (lwlocks, the procarray) grows superlinearly past a few hundred backends. The right value of max_connections on most servers is between 100 and 300; people who set it to 5000 usually wish they had not.

The way to serve more clients than that is a connection pooler in front of the database — almost always PgBouncer. It accepts many client connections, multiplexes them onto a small fixed pool of Postgres connections, and adds latency that is unmeasurable for most workloads.

PgBouncer runs in one of three modes, and the choice has real consequences:

session pooling
One backend per client, released on disconnect. Behaves exactly like a direct connection. No win on concurrency.
transaction pooling
The backend is returned to the pool at every COMMIT / ROLLBACK. The standard choice. Forbids anything stateful across transactions: prepared statements (use PREPARE … EXECUTE at most within one tx), SET (use SET LOCAL), session-scoped advisory locks, LISTEN/NOTIFY, cursors held outside a transaction.
statement pooling
The backend is returned after every statement. Forbids even multi-statement transactions. Almost never the right answer.

The sizing rule of thumb: max_connections on the database equals the sum of pool sizes across all PgBouncer instances, with a little headroom for administrative connections. Picking max_connections = 200 and giving PgBouncer a pool of 180 is normal.

Idle-in-tx, again A pooled connection that the application has handed back without committing leaves a backend stuck in idle in transaction, and pooling does not save you from that. idle_in_transaction_session_timeout is still essential.

pg_stat_statements

The single most useful observability extension Postgres ships. Once loaded, it records — per normalised query — the call count, total and mean execution time, rows returned, buffer hits and reads, and a stable queryid hash. Queries are normalised by replacing literals with placeholders, so SELECT * FROM orders WHERE id = 7 and SELECT * FROM orders WHERE id = 8 collapse to a single row in the view.

Enable it by adding it to shared_preload_libraries (server restart required), then creating the extension in any database you want to query from:

Setup

ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';
-- restart Postgres

CREATE EXTENSION pg_stat_statements;

The single most valuable query against it is "what queries are spending the most cumulative time," because that is where optimisation effort pays back:

Top ten by total time

SELECT round(total_exec_time::numeric / 1000, 1) AS total_s,
       calls,
       round(mean_exec_time::numeric, 2)         AS mean_ms,
       round(100 * total_exec_time
             / sum(total_exec_time) OVER (), 1)  AS pct,
       left(query, 80)                           AS query
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  10;

Result

Three different shapes of problem are visible in three rows: a high-call query with a sub-10 ms mean (the right target for an index check), a moderate-call query with a 50 ms mean (the index probably exists but is missing a column), and a low-call query with a long mean (a reporting query worth running through EXPLAIN). The view does not solve any of them — but it tells you which ones are actually worth your time.

Reset the counters with SELECT pg_stat_statements_reset() when you ship a change and want to measure its effect from scratch.

Configuration & tuning, in one card

shared_buffers
~25% of RAM is the canonical starting point.
effective_cache_size
Planner hint. Set to ~50–75% of RAM. Doesn't allocate anything.
work_mem
Per-sort, per-hash. Multiplied by concurrent operations — be careful.
maintenance_work_mem
Used by VACUUM, CREATE INDEX, ALTER TABLE. Generous is fine.
random_page_cost
Default 4 assumes spinning rust. SSDs want ~1.1.
checkpoint_timeout / max_wal_size
Stretch them to reduce checkpoint frequency on write-heavy workloads.
autovacuum_vacuum_scale_factor
Lower it on hot tables. Default 0.2 lets bloat snowball.
max_connections
Keep low (~100–300). Pool in front with PgBouncer.
pg_stat_statements
Enable it. Top-N queries by total time is your most useful single view.
ALTER SYSTEM
Writes postgresql.auto.conf. SELECT pg_reload_conf() to apply.
