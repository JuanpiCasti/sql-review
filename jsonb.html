JSONB, or, schemaless inside the schema

A binary, indexable, query-able document type that lets you escape the schema when you need to — without leaving the database.

JSONB stores JSON documents in a parsed binary form. Unlike the older json type (which keeps the raw text), jsonb decomposes objects into keys and values once at write time, deduplicates keys, drops insignificant whitespace, and — most importantly — supports operators and indexes that make querying fast. For semi-structured data that varies per row, jsonb turns Postgres into a competent document store without sacrificing the relational machinery for everything else.

json vs jsonb Use jsonb. The only reason to keep json is to preserve the exact input text (whitespace, key order, duplicates) — useful for audit logs, useless for queries.

The operators

Two families: extraction (get a piece out) and predicate (ask a yes/no question, useful in WHERE).

Extraction

doc -> 'key'
Get the value at key as jsonb.
doc ->> 'key'
Get the value at key as text.
doc -> 0
Array element by index; same -> / ->> distinction.
doc #> '{a,b,0}'
Path extraction as jsonb.
doc #>> '{a,b,0}'
Path extraction as text.

Predicates

doc @> subdoc
Contains: does doc contain every key/value (recursively) in subdoc?
doc <@ subdoc
Contained by: the mirror.
doc ? 'key'
Does the top-level document have this key?
doc ?| array
…have any of these keys?
doc ?& array
…have all of these keys?
doc @? path
Does the JSONPath match?
doc @@ path
Does the JSONPath predicate return true?

Extraction vs. predicates

-- payload looks like: {"type": "click", "user": {"id": 7, "tier": "pro"}, "tags": ["a","b"]}

SELECT payload -> 'user'              FROM events;  -- jsonb: {"id":7,"tier":"pro"}
SELECT payload ->> 'type'             FROM events;  -- text:  click
SELECT payload #>> '{user,tier}'      FROM events;  -- text:  pro

SELECT * FROM events WHERE payload @> '{"type": "click"}';   -- containment
SELECT * FROM events WHERE payload ? 'tags';                 -- has top-level key
SELECT * FROM events WHERE payload -> 'tags' ? 'a';          -- array contains 'a'

Indexing — two opclasses

JSONB is indexable with GIN. There are two operator classes to choose from:

jsonb_ops (default)
Indexes every key and value in each document. Supports @>, ?, ?|, ?&, JSONPath. Largest on disk.
jsonb_path_ops
Indexes only paths-to-leaf-values, hashed. Supports @> only. Smaller, faster, often substantially so.

Both indexes, one column

CREATE INDEX events_payload_gin       ON events USING gin (payload);
-- supports @>, ?, ?|, ?&, @?, @@

CREATE INDEX events_payload_path_gin  ON events USING gin (payload jsonb_path_ops);
-- supports @> only — but smaller and faster

-- If your queries are all containment, prefer jsonb_path_ops.
-- If you mix in key-existence (?), keep jsonb_ops.

For queries that hit a specific path repeatedly, a plain B-tree on an expression beats either GIN:

Expression index for hot paths

CREATE INDEX ON events ((payload ->> 'type'));
SELECT * FROM events WHERE payload ->> 'type' = 'click';
-- IndexScan on the B-tree — faster than GIN for this pattern.

JSONPath

JSONPath (SQL/JSON, Postgres 12+) is a small query language for navigating into a document with filters, comparisons, and wildcards. The two operators that use it:

doc @? path
True if the path matches anything.
doc @@ path
True if the path's boolean predicate evaluates to true.

Path queries

-- payload: {"items": [{"sku":"A","qty":1},{"sku":"B","qty":7}]}

-- "does any item have qty > 5?"
SELECT * FROM events
WHERE  payload @? '$.items[*] ? (@.qty > 5)';

-- "all items have qty >= 1"
SELECT * FROM events
WHERE  payload @@ '$.items[*].qty >= 1';

-- extract matching nodes as a set of rows
SELECT jsonb_path_query(payload, '$.items[*] ? (@.qty > 5)')
FROM   events;

JSONPath uses $ for the root, @ for the current node, [*] for "any array element", and ? (...) for filter predicates. It's far more expressive than the simple containment operators, but the planner has weaker statistics for it — expect to want a GIN index to be useful.

Construction and modification

jsonb_build_object(k,v,...)
Build an object from alternating key/value arguments.
jsonb_build_array(...)
Build an array.
to_jsonb(any)
Convert any Postgres value (including a composite row) to jsonb.
row_to_json(row)
Older sibling; returns json not jsonb.
a || b
Concatenate / shallow-merge objects. Right side wins on key conflicts.
doc - 'key'
Remove a top-level key.
doc #- '{a,b}'
Remove a value at a path.
jsonb_set(doc, '{a,b}', new)
Set the value at a path; creates intermediate objects if needed (with create_missing).

Updating a JSONB field in place

UPDATE users
SET    prefs = jsonb_set(prefs, '{theme}', '"dark"', create_missing => true)
WHERE  id = 7;

-- shallow merge with the concatenation operator
UPDATE users
SET    prefs = prefs || '{"theme":"dark","notifications":true}'::jsonb
WHERE  id = 7;
Whole-document rewrite

Every JSONB update rewrites the entire value. There is no in-place patch on disk. For a document that's a few kilobytes and changes one field, that overhead is invisible. For a multi-megabyte document with frequent small updates, it dominates — and you also lose the chance to do HOT updates because the new tuple won't fit on the page. If you're hitting that, the column is too big to be JSONB.

Unnesting JSONB into rows

Three functions convert document structure into ordinary rows you can join, group, and filter:

jsonb_each(doc)
Set of (key, value) pairs from a top-level object.
jsonb_array_elements(arr)
One row per array element.
jsonb_to_recordset(arr)
One row per array element, projected into named columns.

Expanding an array of items

-- payload: [{"sku":"A","qty":1},{"sku":"B","qty":7}]

SELECT e.id, item.sku, item.qty
FROM   events e,
       jsonb_to_recordset(e.payload) AS item(sku text, qty int)
WHERE  item.qty > 5;

The comma in the FROM is an implicit LATERAL CROSS JOIN — the right side runs once per outer row, naturally. (See the joins chapter.)

When not to use JSONB

JSONB is wonderful — and over-used. Move a field out of JSONB into a real column when:

  • Every row has it (so the schemaless flexibility buys you nothing).
  • You query it often, especially in joins.
  • You constrain it (foreign keys, NOT NULL, CHECK).
  • It's a foreign key reference to another table.
  • It's part of an index that needs to support range queries (created_at in JSONB is almost always a mistake).

Move a field into JSONB when it's genuinely sparse (present on a minority of rows), or when the shape is per-tenant / per-customer and changes faster than you can ship migrations.

A useful pattern: hybrid storage. Promote the hot fields to columns, keep the long tail in a metadata jsonb column. The relational engine handles what it's good at; JSONB carries the rest.

A real-world recipe

Event store with the right indexes

CREATE TABLE events (
  id          bigserial PRIMARY KEY,
  type        text      NOT NULL,        -- hot, promoted
  user_id     bigint    NOT NULL,        -- hot, promoted
  occurred_at timestamptz NOT NULL,
  payload     jsonb     NOT NULL         -- everything else
);

-- queries by user + time:
CREATE INDEX ON events (user_id, occurred_at DESC);

-- queries by type + time:
CREATE INDEX ON events (type, occurred_at DESC);

-- containment queries on payload:
CREATE INDEX ON events USING gin (payload jsonb_path_ops);

-- one hot path frequently queried:
CREATE INDEX ON events ((payload ->> 'campaign_id'));

Three different index strategies, each appropriate for a different question. The promoted columns serve OLTP traffic; the GIN index serves ad-hoc analytics; the expression index serves the one report someone runs every hour.

JSONB, in one card

jsonb > json
Binary, indexable, deduplicated keys. Use jsonb.
-> vs ->>
-> returns jsonb, ->> returns text. Same for #> / #>>.
@>
Containment — the workhorse predicate. GIN-indexable.
? ?| ?&
Top-level key existence.
jsonb_ops
Default GIN opclass. Supports @>, ?, ?|, ?&, path ops.
jsonb_path_ops
Smaller, faster — but @> only.
Expression index
For hot specific paths: ((payload ->> 'k')). Beats GIN for equality.
@? / @@
JSONPath: navigate, filter, predicate.
jsonb_set / ||
Modify; whole document rewritten each time.
jsonb_to_recordset
Expand an array of objects into named columns.
Promote columns
Hot, always-present, joined, constrained — pull out of jsonb.
