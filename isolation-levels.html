Isolation levels, or, what your snapshot sees

The contract Postgres offers between concurrent transactions — and the four anomalies it lets you choose to prevent.

Isolation is the I in ACID. It is the database's answer to a single, slippery question: when many transactions run at once, which of each other's effects should they be allowed to see? The SQL standard names four levels — Read Uncommitted, Read Committed, Repeatable Read, Serializable — defined by which anomalies each one forbids. Postgres implements three of them (it has no dirty reads, ever) using a single underlying mechanism: multi-version snapshots.

A note Postgres accepts the syntax READ UNCOMMITTED but treats it as READ COMMITTED. There is no way to see another transaction's uncommitted writes in Postgres — a property worth a paragraph of its own in interviews.

The four anomalies

The standard defines isolation negatively: a level is described by what it forbids. Four phenomena have names worth memorising.

Dirty read
Reading a row another transaction has written but not yet committed. Never happens in Postgres at any level.
Non-repeatable read
Reading the same row twice in one transaction and getting two different values, because a concurrent transaction committed an UPDATE in between.
Phantom read
Re-running the same range query and seeing rows that weren't there before, because a concurrent transaction committed an INSERT matching the predicate.
Serialization anomaly
A set of transactions that each ran successfully produces a result that could not have been produced by running them one at a time in any order. The subtle one. Examples below.

Read Committed — the default

At Read Committed, every statement sees a fresh snapshot of the database as of the moment that statement began. Two statements in the same transaction therefore can see different things, because committed work from other sessions slips in between them.

This is what the non-repeatable read anomaly looks like in practice. Session A reads the same row twice and sees two different values:

t
Session A
Session B
t1
BEGIN;
t2
SELECT balance FROM accounts WHERE id=1; -- 100
t3
UPDATE accounts SET balance=150 WHERE id=1;
COMMIT;
t4
SELECT balance FROM accounts WHERE id=1; -- 150 !
t5
COMMIT;

Each statement in A is internally consistent (it sees a single point-in-time snapshot), but successive statements see successive snapshots. For most OLTP workloads this is exactly what you want — readers never block writers, writers never block readers, and stale data is bounded to the duration of a single statement.

A subtle point

If an UPDATE or DELETE at Read Committed finds that the row it's about to modify has been changed by a concurrent transaction that has since committed, Postgres does not abort. It re-reads the latest committed version, re-evaluates the WHERE clause against it, and applies the update if it still matches. This is called the EvalPlanQual retry. It keeps Read Committed usable, but it means a single UPDATE can see a different snapshot than the surrounding SELECTs.

Repeatable Read — snapshot isolation

At Repeatable Read, the snapshot is taken once, at the first non-transaction-control statement of the transaction, and every subsequent read in the transaction sees that same snapshot. The non-repeatable read seen under Read Committed cannot happen: A's second SELECT returns 100, not 150, because B's commit happened after A's snapshot.

Postgres's Repeatable Read is what the literature calls snapshot isolation. It also prevents the standard's phantom read — a re-run of SELECT count(*) FROM orders WHERE total > 100 returns the same count both times.

What it does not prevent is the serialization anomaly. The canonical example is the write skew:

t
Session A (on call: alice)
Session B (on call: bob)
t1
BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN ISOLATION LEVEL REPEATABLE READ;
t2
SELECT count(*) FROM doctors WHERE on_call; -- 2
SELECT count(*) FROM doctors WHERE on_call; -- 2
t3
UPDATE doctors SET on_call=false WHERE name='alice';
UPDATE doctors SET on_call=false WHERE name='bob';
t4
COMMIT; -- ok
COMMIT; -- ok
Result: no doctors on call. Each transaction was internally consistent; together they broke an invariant ("at least one doctor must always be on call") that neither transaction violated on its own.

Each transaction read 2 from the same snapshot, decided it was safe to take one off, and committed. There is no serial schedule of A and B that produces this outcome, but RR allows it because neither transaction wrote to a row the other read.

When RR is right Repeatable Read is the right default for reports, dashboards, exports — anything that runs many SELECTs and needs them all to agree, but doesn't write data that depends on what it read.

At Repeatable Read, two transactions that try to modify the same row are still serialised: the second one waits for the first, and if the first commits, the second aborts with ERROR: could not serialize access due to concurrent update. Your application must catch this SQLSTATE (40001) and retry the transaction from the start.

Serializable — SSI

Serializable in Postgres is implemented with Serializable Snapshot Isolation (SSI, Cahill 2008). It begins as ordinary snapshot isolation, then monitors read–write dependencies between concurrent transactions in the background. If it detects a pattern that could produce an anomaly — a "dangerous structure" of rw-antidependencies — it aborts one of the transactions with the same 40001 serialization failure.

Re-run the doctors example under Serializable and one of the two commits will fail:

t
Session A
Session B
t1
BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN ISOLATION LEVEL SERIALIZABLE;
t2
SELECT count(*) FROM doctors WHERE on_call; -- 2
SELECT count(*) FROM doctors WHERE on_call; -- 2
t3
UPDATE doctors SET on_call=false WHERE name='alice';
UPDATE doctors SET on_call=false WHERE name='bob';
t4
COMMIT; -- ok
COMMIT;
ERROR: could not serialize access
due to read/write dependencies
among transactions

The error message even suggests the remedy: "The transaction might succeed if retried." Retry-on-40001 is the application-level contract that Serializable requires.

The price

SSI tracks predicate locks on every row, page, and index range a transaction reads. Under high contention this overhead is real, and false positives — aborts of transactions that would have been safe — are part of the design. Use Serializable when correctness justifies it (financial postings, multi-row invariants); otherwise prefer Read Committed with explicit row locks for the rows you mean to protect.

Two more notes:

  • SERIALIZABLE READ ONLY DEFERRABLE waits for a "safe snapshot" before starting, after which it will never abort. Perfect for long analytic queries on a busy OLTP database.
  • SSI is per-database. Cross-database transactions (using foreign data wrappers) fall back to snapshot isolation regardless of declared level.

Choosing a level

A practical decision rule:

  • Read Committed for everything OLTP by default. It's what your migrations, your background jobs, and 95% of your application code want.
  • Repeatable Read when one transaction issues many SELECTs that must agree (reports, dashboard pages, exports, replication tooling) and doesn't write anything dependent on what it read.
  • Serializable when you have multi-row invariants — counts, totals, "at least one of X" — that two concurrent writers could each independently uphold while jointly violating. Be prepared to retry.

You change the level per-transaction (BEGIN ISOLATION LEVEL …), per-session (SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL …), or globally via the GUC default_transaction_isolation.
