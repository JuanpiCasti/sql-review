Schema design, or, what the database refuses to allow

A constraint is a guarantee the database makes on your behalf — a rule that no bug, no race, and no junior engineer with a psql prompt can violate.

Most data corruption is preventable in the schema. Foreign keys catch the orphan rows, CHECK constraints catch the impossible values, exclusion constraints catch the overlapping reservations. This chapter is the constraint vocabulary: what each one enforces, what it costs, and which ones earn their keep in production schemas.

Constraints, in one card

PRIMARY KEY
Unique + not null + the table's default row identity.
FOREIGN KEY
Row in this table must reference an existing row in the parent.
ON DELETE CASCADE
Parent delete propagates. RESTRICT is the safer default.
UNIQUE
No two rows share these values. NULLs do not collide.
CHECK (expr)
Row-level boolean. Must be IMMUTABLE; no subqueries.
EXCLUDE
"No two rows where these predicates overlap." GiST-backed.
NOT NULL
The cheapest, highest-leverage constraint in the catalog.
GENERATED ALWAYS AS
Column computed from other columns. Stored or virtual.
DEFERRABLE
Check at COMMIT instead of per-statement. Needed for cyclic FKs.
Adding NOT NULL
Use a CHECK NOT VALID + VALIDATE on big tables to avoid the long lock.
