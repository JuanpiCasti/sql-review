Foundations

Schema design, or, what the database refuses to allow

A constraint is a guarantee the database makes on your behalf — a rule that no bug, no race, and no junior engineer with a psql prompt can violate.

Most data corruption is preventable in the schema. Foreign keys catch the orphan rows, CHECK constraints catch the impossible values, exclusion constraints catch the overlapping reservations. This chapter is the constraint vocabulary: what each one enforces, what it costs, and which ones earn their keep in production schemas.

CREATE TABLE anatomy

A table declaration is part data shape, part contract. The shape is the column list — names and types. The contract is everything else: defaults, nullability, per-row checks, multi-column keys, references to other tables. Every constraint you bake into the CREATE TABLE is a guarantee the database will keep on your behalf for the rest of the table's life.

A realistic declaration uses both column-level and table-level constraints:

A booking table with one of each constraint kind

CREATE TABLE IF NOT EXISTS bookings (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id     int          NOT NULL REFERENCES rooms (id),
  guest_email text         NOT NULL CHECK (guest_email ~ '@'),
  starts_at   timestamptz  NOT NULL,
  ends_at     timestamptz  NOT NULL,
  created_at  timestamptz  NOT NULL DEFAULT now(),
  status      text         NOT NULL DEFAULT 'pending',

  CONSTRAINT bookings_time_order CHECK (ends_at > starts_at),
  CONSTRAINT bookings_status_known
    CHECK (status IN ('pending', 'confirmed', 'cancelled')),
  CONSTRAINT bookings_room_slot_unique UNIQUE (room_id, starts_at)
);

The column-level constraints (NOT NULL, DEFAULT, inline REFERENCES, inline single-column CHECK) describe one column at a time. The table-level constraints below the column list describe rules that span columns: ends_at > starts_at is two columns; UNIQUE (room_id, starts_at) is composite. Anything that involves more than one column has to live at the table level.

Two clauses every schema author should know:

IF NOT EXISTS
Make the CREATE TABLE idempotent. Useful in migration scripts you might re-run; harmless when the table already exists.
LIKE source_table INCLUDING ALL
Copy a table's column list, defaults, constraints, indexes, and storage settings into a new table. The shape is copied; the data is not. Handy for partition templates and staging tables.

Two table kinds worth mentioning in passing. CREATE TEMP TABLE creates a session-local table that disappears at the end of the session, useful inside complex one-shot scripts. CREATE UNLOGGED TABLE skips writing to the WAL — inserts are dramatically faster, but the table is truncated on crash and not replicated. Right for ephemeral caches, scratch space, and import staging; wrong for anything you care about.

Primary keys — surrogate vs natural

Every table should have a primary key. Postgres does not require one — you can create a table without — but logical replication, most ORMs, UPDATE/DELETE tooling, and your future debugging self all assume one exists. Treat "no primary key" as a bug.

The choice is between a surrogate key (a meaningless identifier the database mints) and a natural key (a column or composite of columns that already identifies the row by its real-world meaning).

Surrogate: a synthetic identifier the application never inspects

CREATE TABLE customers (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE,
  name  text NOT NULL
);

Natural: a composite key that identifies the tuple by its meaning

CREATE TABLE order_lines (
  order_id bigint NOT NULL REFERENCES orders (id),
  line_no  int    NOT NULL,
  sku      text   NOT NULL,
  qty      int    NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, line_no)
);

Natural keys are appealing — the email is the user, the ISBN is the book — until the real world contradicts you. Emails change. People get married. ISBNs get reassigned. Country codes get renamed. Anywhere the "identifying" column might mutate, a surrogate key turns a multi-table cascading update into a one-table profile change. The pragmatic rule: surrogate for entities (rows that represent things in the world), natural for relationships (rows that exist because two entities are connected). order_lines above is correctly natural; customers is correctly surrogate.

Three ways to spell the surrogate:

bigserial
The legacy macro: creates a sequence, binds it as the column default, and "owns" the sequence with the table. Works fine; semantics are subtly looser than the SQL standard form (users can override the default by writing an explicit value, which can clash with the sequence later).
bigint GENERATED ALWAYS AS IDENTITY
The SQL-standard form, recommended for new code. Identical storage; tighter semantics — ALWAYS means inserts cannot override the value without explicit OVERRIDING SYSTEM VALUE. The sequence is managed declaratively and is easy to alter.
uuid DEFAULT gen_random_uuid()
128-bit, client-mintable, opaque. Twice the storage; worse B-tree locality for v4 random values. Right when the ID must be generated outside the database. See Data types & NULL for the trade-offs.
Idiom In new schemas, GENERATED ALWAYS AS IDENTITY is the right default. bigserial is everywhere in legacy code and isn't worth migrating mid-project, but reach for the standard form when you have the choice.

Foreign keys and ON DELETE actions

A foreign key says: every value in this column must already exist in that column of that other table. The database refuses inserts and updates that would create an orphan, and it refuses to delete a parent row that would strand its children — unless you have told it, in advance and in writing, what to do instead.

Two syntactic forms, identical in what they enforce. The inline column-constraint form for the single-column case:

Inline form

CREATE TABLE orders (
  id          bigserial PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers (id),
  placed_at   timestamptz NOT NULL DEFAULT now()
);

And the table-level form, which you need whenever the key spans more than one column or you want to name the constraint yourself:

Table-level form, composite key

CREATE TABLE order_lines (
  order_id   bigint NOT NULL,
  line_no    int    NOT NULL,
  sku        text   NOT NULL,
  qty        int    NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, line_no),
  CONSTRAINT order_lines_order_fk
    FOREIGN KEY (order_id) REFERENCES orders (id)
    ON DELETE CASCADE
);

The referenced column(s) must be the parent's PRIMARY KEY or carry a UNIQUE constraint — Postgres needs a unique index to check the reference against, and it will refuse the CREATE TABLE otherwise. That index exists on the parent side for free. The child side gets nothing: there is no automatic index on orders.customer_id, and you almost always want to add one yourself.

The five referential actions

Both ON DELETE and ON UPDATE accept the same five actions, describing what happens to the child rows when the parent is removed or its key changes:

NO ACTION
The default. Raise an error if any child still references the parent. The check is performed at the end of the statement and can be deferred to COMMIT with DEFERRABLE.
RESTRICT
Same outcome as NO ACTION in the common case, but the check fires immediately and cannot be deferred. Use it when you want to forbid the operation outright with no escape hatch.
CASCADE
Delete the children too, or propagate the new key value to them. Convenient and dangerous in equal measure — a single DELETE can fan out across half the database.
SET NULL
Null the child's referencing column. The column must of course be nullable. You can optionally restrict it to a subset of the FK columns: ON DELETE SET NULL (customer_id).
SET DEFAULT
Set the child's referencing column to its declared DEFAULT. If that default does not itself satisfy the foreign key, the action fails at the moment it fires, not at constraint creation.
Under the hood Foreign-key enforcement takes a FOR KEY SHARE row lock on the parent row for every insert or update of a child. That weaker mode exists precisely so two transactions inserting different children of the same parent don't block each other — see Locking & deadlocks.
Pitfall

Postgres does not create an index on the child's referencing column. Every DELETE or key-changing UPDATE on the parent must then scan the entire child table to find rows that might point at the row going away. On a million-row child this is the difference between a millisecond and a minute. If you write REFERENCES customers (id), write CREATE INDEX ON orders (customer_id); on the next line.

Deferring the check for cyclic references

Some schemas are unavoidably circular — an employees table where every row references its manager, or a pair of tables that reference each other. A strict per-statement check makes the very first INSERT impossible: there is no row to reference yet. The fix is to mark the constraint DEFERRABLE and let Postgres postpone the check to COMMIT:

Self-referential FK, deferred

CREATE TABLE employees (
  id         bigserial PRIMARY KEY,
  name       text NOT NULL,
  manager_id bigint REFERENCES employees (id)
    DEFERRABLE INITIALLY DEFERRED
);

BEGIN;
INSERT INTO employees (id, name, manager_id) VALUES (1, 'Ada',   2);
INSERT INTO employees (id, name, manager_id) VALUES (2, 'Grace', 1);
COMMIT;  -- both rows exist; the check passes here, not above

You can also leave it INITIALLY IMMEDIATE and switch on demand inside a transaction with SET CONSTRAINTS ALL DEFERRED. What you cannot do is deferrability via ALTER: a constraint that was created without DEFERRABLE can never be deferred. If you might ever want to defer it, declare it deferrable up front. RESTRICT, by definition, is never deferrable regardless.

Adding a foreign key to a big table

The naive ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY takes a SHARE ROW EXCLUSIVE lock on both tables and scans the child to validate every existing row. On a hot table that is downtime. The two-step does the validation without the long lock:

Online FK addition

ALTER TABLE orders
  ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers (id)
  NOT VALID;                       -- enforces on new rows only; quick

ALTER TABLE orders
  VALIDATE CONSTRAINT orders_customer_fk;  -- scans existing rows; weaker lock

The NOT VALID constraint begins enforcing on every subsequent INSERT and UPDATE immediately; the later VALIDATE only has to confirm the pre-existing rows. The pattern generalises to CHECK constraints too, and is the subject of the Safe vs locking ALTER TABLE section below.

CHECK, UNIQUE, EXCLUDE

Three constraint types past the foreign key, three different jobs. CHECK validates a row against itself, UNIQUE validates a row against the rest of the table by exact match, EXCLUDE validates a row against the rest of the table by an arbitrary operator.

CHECK

A row-level boolean predicate. The constraint fires on every INSERT and UPDATE; if the expression evaluates to false the statement raises 23514. NULL is treated as "satisfied," which sometimes surprises people — CHECK (col > 0) still allows NULL in col unless you also write NOT NULL.

Single-column and cross-column CHECKs

CREATE TABLE invoices (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  subtotal    numeric(12, 2) NOT NULL CHECK (subtotal >= 0),
  tax         numeric(12, 2) NOT NULL CHECK (tax >= 0),
  total       numeric(12, 2) NOT NULL,
  issued_at   timestamptz NOT NULL,
  due_at      timestamptz NOT NULL,

  CONSTRAINT invoices_total_sums  CHECK (total = subtotal + tax),
  CONSTRAINT invoices_due_after   CHECK (due_at >= issued_at)
);

The expression must be IMMUTABLE — no now(), no random(), no subqueries, no references to other tables. Postgres enforces this at constraint-creation time: writing CHECK (created_at < now()) is rejected with cannot use volatile function … in check constraint. The reason is that the check must be reproducible — a stored row that satisfied the constraint on insert must still satisfy it on a later pg_dump reload, and a non-deterministic predicate can't make that guarantee.

UNIQUE

A uniqueness constraint, backed by a unique B-tree index. The index is automatically created and dropped with the constraint; you can name the constraint, and the index inherits the name. UNIQUE can be inline (single column) or table-level (composite).

The default NULL semantics are the trap: two NULLs are not considered equal, so a UNIQUE column happily accepts as many NULL rows as you can throw at it. Postgres 15 added NULLS NOT DISTINCT to flip that:

Default NULL semantics vs NULLS NOT DISTINCT

CREATE TABLE a (email text UNIQUE);
INSERT INTO a VALUES (NULL), (NULL);   -- both succeed

CREATE TABLE b (email text UNIQUE NULLS NOT DISTINCT);
INSERT INTO b VALUES (NULL);
INSERT INTO b VALUES (NULL);
-- ERROR:  duplicate key value violates unique constraint "b_email_key"
-- SQLSTATE: 23505

The other common pattern is a partial unique index — uniqueness that only applies to a subset of rows. Postgres expresses this as a unique index with a WHERE clause, not as a UNIQUE constraint:

"Only one active row per user"

CREATE UNIQUE INDEX one_active_subscription_per_user
  ON subscriptions (user_id)
  WHERE status = 'active';

Inactive rows can repeat freely; the database guarantees there is at most one active subscription per user. This pattern is everywhere — soft-deleted rows, draft documents, current employer of an employee — and is impossible to express with a plain UNIQUE constraint.

EXCLUDE

The most powerful and least known of the three. An EXCLUDE constraint says: "no two rows where these column pairs satisfy these operators." Plain UNIQUE is the special case where all the operators are =. Replace any of them with && (range overlap), &< (geometric strictly-left-of), or any other operator with an operator-class definition, and you get constraints no other relational database can express declaratively.

The canonical example is non-overlapping reservations:

Non-overlapping bookings, enforced by the database

CREATE EXTENSION IF NOT EXISTS btree_gist;  -- lets '=' work inside GiST

CREATE TABLE bookings (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id int       NOT NULL,
  during  tstzrange NOT NULL,

  EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

INSERT INTO bookings (room_id, during)
VALUES (1, '[2026-05-21 09:00+00, 2026-05-21 10:00+00)');

INSERT INTO bookings (room_id, during)
VALUES (1, '[2026-05-21 09:30+00, 2026-05-21 10:30+00)');
-- ERROR:  conflicting key value violates exclusion constraint
--         "bookings_room_id_during_excl"
-- SQLSTATE: 23P01

The constraint is enforced by a GiST index in the background — see Indexes for the index side of the story. Outside ranges, exclusion constraints handle geometric non-overlap (no two polygons touching), interval-tree problems, and any "no two rows are in conflict by X" rule you would otherwise have written a flaky trigger for.

Why not a trigger?

Triggers can implement non-overlap rules — and almost every implementation people write is subtly broken under concurrency. Two transactions checking "does an overlapping booking exist?" in parallel both see no conflict, both insert, and you have a double-booking. EXCLUDE is enforced through the index in the same code path as UNIQUE: atomic, race-free, and declared, not coded.

NOT NULL and defaults

The cheapest, highest-leverage constraint in the catalog — and the one that requires the most care to add to an existing big table. Every nullable column is a small tax on every query that touches it: three-valued logic propagates through every predicate (see Data types & NULL), NOT IN traps wait quietly, and joins on nullable keys behave in ways that surprise newcomers.

A nullable column changes an aggregate

CREATE TABLE t (id int, score int);
INSERT INTO t VALUES (1, 80), (2, NULL), (3, 90);

SELECT count(*)   AS rows,
       count(score) AS scored,
       avg(score) AS mean
FROM t;

Result

rowsscoredmean
3285.0000000000000000

The mean is 85, not 56.67 — Postgres correctly skipped the NULL, but the reader may not have wanted that. Every aggregate, every WHERE, every JOIN ON across that column has to make a similar decision. The simplest fix is the strongest one: make the column NOT NULL if the data permits, with a sensible default.

Defaults

A default fills in a value when the column is omitted from INSERT. Defaults are evaluated per row at insert time, not once per statement, so volatile defaults like now() and gen_random_uuid() produce a fresh value for each row. Constant defaults (0, 'pending', false) cost nothing — since PG 11 they're stored as metadata and applied virtually until the column is rewritten.

Common default idioms

CREATE TABLE events (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  trace_id    uuid        NOT NULL DEFAULT gen_random_uuid(),
  occurred_at timestamptz NOT NULL DEFAULT now(),
  kind        text        NOT NULL DEFAULT 'unknown',
  payload     jsonb       NOT NULL DEFAULT '{}'::jsonb
);

Adding NOT NULL to a big table

The naive command takes an ACCESS EXCLUSIVE lock on the table and scans every row to verify none are null. On a billion-row table that is real downtime. The two-step pattern uses a CHECK constraint to do the same validation under a weaker lock:

Online NOT NULL addition

-- 1. Add the constraint without scanning. Brief ACCESS EXCLUSIVE on metadata
--    only; enforces on every new INSERT/UPDATE from this moment on.
ALTER TABLE events
  ADD CONSTRAINT events_kind_not_null
  CHECK (kind IS NOT NULL) NOT VALID;

-- 2. Scan the existing rows under SHARE UPDATE EXCLUSIVE — reads and writes
--    proceed in parallel.
ALTER TABLE events
  VALIDATE CONSTRAINT events_kind_not_null;

-- 3. (PG 12+) Promote to a real NOT NULL. The planner uses the validated
--    CHECK to skip a second scan; the operation is metadata-only.
ALTER TABLE events
  ALTER COLUMN kind SET NOT NULL;

ALTER TABLE events
  DROP CONSTRAINT events_kind_not_null;   -- redundant once SET NOT NULL stuck

The pattern is the same as the online foreign-key addition above: NOT VALID to start enforcing on new rows immediately, then VALIDATE to mop up the existing ones without holding the strong lock. This is the central pattern of online schema change in Postgres; the next section is dedicated to it.

Why two steps NOT VALID means "valid going forward, possibly violated by old rows." VALIDATE means "scan the old rows and confirm." Splitting them lets you absorb the cheap operation under a strong lock and the expensive one under a weak lock — the opposite of the naive single command.

Generated columns

A generated column is a column whose value is derived from other columns in the same row, computed by the database at insert and update time. The expression is part of the schema; the value is not a thing the application writes. The syntax is GENERATED ALWAYS AS (expr) STORED.

A denormalised total, indexed and queryable

CREATE TABLE order_lines (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  unit_price  numeric(12, 2) NOT NULL CHECK (unit_price >= 0),
  qty         int            NOT NULL CHECK (qty > 0),
  line_total  numeric(14, 2) GENERATED ALWAYS AS (unit_price * qty) STORED
);

CREATE INDEX order_lines_big ON order_lines (line_total) WHERE line_total > 1000;

INSERT INTO order_lines (unit_price, qty) VALUES (19.99, 3) RETURNING *;

Result

idunit_priceqtyline_total
119.99359.97

Three rules constrain the expression: it must be deterministic (no now(), no random(), no volatile functions), it may reference only columns in the same row (no subqueries, no other tables), and it cannot reference other generated columns. Attempts to INSERT or UPDATE the column directly raise an error — the only way to change line_total is to change unit_price or qty.

Postgres only implements the STORED variant. The SQL standard also defines VIRTUAL generated columns (computed on read, not stored on disk), and Postgres parses the keyword but rejects it. If you want virtual semantics, write a regular column-less VIEW.

Common uses where generated columns earn their keep:

Search vectors
tsvector generated from a concatenation of text columns — the search column is always in sync with its sources, no triggers required. See Full-text search.
Normalised lowercase forms
email_lower text GENERATED ALWAYS AS (lower(email)) STORED for case-insensitive unique constraints and lookups.
Denormalised aggregates
Per-row totals, durations (ends_at - starts_at), JSON path extracts pulled into a typed column for indexing.

Safe vs locking ALTER TABLE

Every ALTER TABLE takes a lock. The question is which lock and for how long. ACCESS EXCLUSIVE — the strongest — blocks every concurrent reader and writer, including a one-row SELECT; holding it for ten seconds on a busy production table is ten seconds of stalled application traffic. The art of online schema change is doing the same logical operation without holding ACCESS EXCLUSIVE while the table is scanned.

The general patterns:

Common operations and what they actually lock

OperationLockCost
ADD COLUMN, nullable, no defaultACCESS EXCLUSIVE (brief)Metadata-only since PG 11. Instant.
ADD COLUMN … DEFAULT <constant>ACCESS EXCLUSIVE (brief)Metadata-only since PG 11; default applied virtually until rewrite.
ADD COLUMN … DEFAULT <volatile>ACCESS EXCLUSIVE (long)Rewrites the entire table. Avoid; add the column nullable, backfill in batches, then SET NOT NULL.
DROP COLUMNACCESS EXCLUSIVE (brief)Metadata-only. Storage reclaimed by future VACUUM FULL or rewrite.
ALTER COLUMN TYPEACCESS EXCLUSIVE (long)Usually rewrites the table; rewrites the indexes. varchar(n) → text and similar same-binary conversions are metadata-only.
CREATE INDEXSHAREBlocks writes; allows reads. Long on big tables.
CREATE INDEX CONCURRENTLYSHARE UPDATE EXCLUSIVEAllows reads and writes. Two table scans; longer overall.
ADD FK / CHECK + NOT VALIDACCESS EXCLUSIVE (brief)Enforces on new rows immediately; pre-existing rows skipped.
VALIDATE CONSTRAINTSHARE UPDATE EXCLUSIVEScans existing rows; allows reads and writes.
SET NOT NULLACCESS EXCLUSIVEBrief if a validated CHECK (col IS NOT NULL) already exists (PG 12+); otherwise a full scan under the strong lock.

The recurring move is to split a single operation into two halves: a fast metadata change under ACCESS EXCLUSIVE, and a slow scan under a lighter lock that allows the application to keep running.

CREATE INDEX CONCURRENTLY

Building an index under the default SHARE lock blocks every writer for the duration of the build. CONCURRENTLY uses a weaker SHARE UPDATE EXCLUSIVE lock that allows reads and writes to proceed. The trade-offs are real: two passes over the table instead of one (slower overall), no other DDL can run on the table at the same time, and the operation cannot run inside a transaction block.

Online index build, with cleanup if it fails

CREATE INDEX CONCURRENTLY orders_customer_idx ON orders (customer_id);

-- If the build is interrupted, the index exists but is marked INVALID and
-- the planner will not use it. Find and drop the corpse before retrying:
SELECT c.relname
FROM   pg_index i
JOIN   pg_class c ON c.oid = i.indexrelid
WHERE  NOT i.indisvalid;

DROP INDEX CONCURRENTLY orders_customer_idx;
CREATE INDEX CONCURRENTLY orders_customer_idx ON orders (customer_id);
Pitfall

Always set a short lock_timeout before running production DDL: SET lock_timeout = '2s';. Without it, an ALTER TABLE that can't immediately acquire ACCESS EXCLUSIVE queues behind whatever long-running query holds a lighter lock — and every subsequent query on the table queues behind your waiting DDL. One slow analytic SELECT plus one unguarded ALTER TABLE is enough to take down a hot table for ten minutes. A short lock_timeout turns the failure mode from "outage" into "migration retry."

Constraints, in one card

PRIMARY KEY
Unique + not null + the table's default row identity.
FOREIGN KEY
Row in this table must reference an existing row in the parent.
ON DELETE CASCADE
Parent delete propagates. RESTRICT is the safer default.
UNIQUE
No two rows share these values. NULLs do not collide.
CHECK (expr)
Row-level boolean. Must be IMMUTABLE; no subqueries.
EXCLUDE
"No two rows where these predicates overlap." GiST-backed.
NOT NULL
The cheapest, highest-leverage constraint in the catalog.
GENERATED ALWAYS AS
Column computed from other columns. Stored or virtual.
DEFERRABLE
Check at COMMIT instead of per-statement. Needed for cyclic FKs.
Adding NOT NULL
Use a CHECK NOT VALID + VALIDATE on big tables to avoid the long lock.
