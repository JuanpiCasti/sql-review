Full-text search, or, LIKE '%foo%' considered harmful

A search engine inside the database — stemming, ranking, phrase queries, and a GIN index that turns a sequential scan of millions of documents into a few milliseconds.

Postgres ships with a credible full-text engine: tokenisers for two dozen languages, configurable stemmers, phrase and proximity operators, and a ranking function. For the search bar on a moderately busy app, it is almost always enough — and it spares you the operational cost of running a second datastore. This chapter covers what's in the box.

tsvector and tsquery

The whole machinery rests on two types. A tsvector is a sorted, deduplicated list of lexemes — normalised root forms of the words in a document — each carrying the positions where it appeared in the source text. A tsquery is a parsed boolean expression over lexemes, with operators for AND, OR, NOT, and phrase distance. Matching is the predicate that decides whether a query's tree evaluates to true against a vector.

A vector contains lexemes, not words

SELECT to_tsvector('english', 'The quick brown foxes were jumping over the lazy dogs');

Result

to_tsvector
'brown':3 'dog':10 'fox':4 'jump':6 'lazi':9 'quick':2

Three things to notice in that result. The stop words (the, were, over) are gone — the english configuration drops them. The remaining words have been stemmed — foxes → fox, jumping → jump, lazy → lazi. And each lexeme carries its position in the original token stream, which is what makes phrase queries possible.

Queries come in three flavours, each parsing input differently. to_tsquery expects operator-laden input (& / | / ! / <->) and is unsuitable for user-provided strings; plainto_tsquery takes plain text and ANDs the terms; websearch_to_tsquery implements the Google-style syntax most users already know — quoted phrases, OR, leading - for exclusion.

The three query parsers, side by side

SELECT to_tsquery        ('english', 'quick & !lazy')          AS strict,
       plainto_tsquery   ('english', 'quick brown foxes')     AS plain,
       websearch_to_tsquery('english', '"brown fox" OR -lazy') AS web;

Result

strictplainweb
'quick' & !'lazi''quick' & 'brown' & 'fox''brown' <-> 'fox' | !'lazi'

The <-> in the last result is the phrase-distance operator: brown immediately followed by fox. <N> with a number relaxes "immediately" to "within N positions."

Dictionaries, stemmers, configurations

The pipeline from raw text to tsvector runs through a text search configuration, which is itself a chain: a parser tokenises the input into typed tokens (word, email, url, num, …), and each token type is passed through an ordered list of dictionaries. The first dictionary that recognises a token decides what lexeme — if any — to emit.

The shipped english configuration wires the default parser to a stop-word filter (english_stem's stop list) and the Snowball English stemmer. Same shape for the two dozen other languages Postgres ships with. You can see exactly what a configuration is doing with ts_debug:

Per-token tracing

SELECT alias, token, dictionary, lexemes
FROM ts_debug('english', 'Running queries against PostgreSQL');

against emits an empty lexeme set — it is in the stop list. The lexemes you actually want to customise — accents folded, brand-name synonyms collapsed, custom stop words — are configured by building a new configuration and inserting different dictionaries into the pipeline.

An accent-folding configuration

CREATE EXTENSION IF NOT EXISTS unaccent;

CREATE TEXT SEARCH CONFIGURATION en_unaccent ( COPY = english );
ALTER TEXT SEARCH CONFIGURATION en_unaccent
  ALTER MAPPING FOR hword, hword_part, word
  WITH unaccent, english_stem;

SELECT to_tsvector('en_unaccent', 'café cliché naïve');

Result

to_tsvector
'cafe':1 'cliche':2 'naive':3
Default The session's default configuration comes from default_text_search_config. Set it per database (ALTER DATABASE app SET default_text_search_config = 'pg_catalog.english') so application code can omit the first argument to to_tsvector without surprise.

@@ and ranking with ts_rank

The match operator is @@. It returns true if a tsvector satisfies a tsquery, and is the predicate you put in the WHERE clause of every full-text search.

A basic match

SELECT id, title
FROM   articles
WHERE  to_tsvector('english', title || ' ' || body)
       @@ websearch_to_tsquery('english', 'postgres "full text"');

Match returns a boolean. To order results, you need a score — and Postgres gives you two ranking functions that produce one. ts_rank weights matches by frequency: a document that mentions the query terms more often ranks higher. ts_rank_cd ("coverage density") additionally rewards matches whose terms appear close together in the source; if your users expect phrase-like results to rise to the top, it is usually what you want.

Top ten by relevance

WITH q AS (SELECT websearch_to_tsquery('english', 'replication slot') AS query)
SELECT a.id, a.title,
       ts_rank_cd(to_tsvector('english', a.body), q.query) AS rank
FROM   articles a, q
WHERE  to_tsvector('english', a.body) @@ q.query
ORDER  BY rank DESC
LIMIT  10;

Result

idtitlerank
418Replication slots in depth0.187
221What WAL is for0.094
503Logical decoding in production0.061

Neither ranker is normalised — the absolute scores are meaningless across queries, only relative ordering within one query is. Both accept a fourth argument with weighting flags (A, B, C, D) so titles can outrank body matches; you assign those weights at vector-construction time with setweight.

Title beats body

SELECT setweight(to_tsvector('english', title), 'A')
    || setweight(to_tsvector('english', body),  'D') AS doc
FROM articles
WHERE id = 418;

GIN-indexing a tsvector

Without an index, @@ is a sequential scan: every row, every document, tokenised on the fly. That is fine for a thousand rows and ruinous past a hundred thousand. The right index is GIN ("generalized inverted index"), which under the hood stores a posting list per lexeme — a lookup from word to the row IDs that contain it, exactly as a search engine would.

There are two ways to wire it up. The expression-index form indexes the result of to_tsvector(...) at write time, but every query must use the same expression for the planner to recognise the match:

Expression index — query must mirror it exactly

CREATE INDEX articles_body_gin
  ON articles
  USING GIN (to_tsvector('english', body));

-- Uses the index:
SELECT id FROM articles
WHERE to_tsvector('english', body) @@ websearch_to_tsquery('english', 'wal');

-- Does NOT (different configuration argument shape):
SELECT id FROM articles
WHERE to_tsvector(body) @@ websearch_to_tsquery('wal');

The more durable pattern is a generated column of type tsvector, indexed directly. Postgres maintains it on every write, the type is now first-class data, and every query trivially matches the index. From PG 12 onwards this is the recommended shape.

Stored generated column, the modern shape

ALTER TABLE articles
  ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title,'')), 'A') ||
    setweight(to_tsvector('english', coalesce(body, '')), 'D')
  ) STORED;

CREATE INDEX articles_search_gin ON articles USING GIN (search);

EXPLAIN SELECT id FROM articles
WHERE  search @@ websearch_to_tsquery('english', 'replication slot');

Result

QUERY PLAN
Bitmap Heap Scan on articles (cost=24.0..189.4 rows=42 width=8)
Recheck Cond: (search @@ '''replic'' & ''slot'''::tsquery)
-> Bitmap Index Scan on articles_search_gin
Index Cond: (search @@ '''replic'' & ''slot'''::tsquery)
Note

GIN's write cost is real. To soften it, Postgres batches updates into a pending list (fastupdate = on) that is flushed when it grows past gin_pending_list_limit or vacuum runs. On insert-heavy tables this is exactly what you want; on read-heavy tables the pending list adds a recheck step to every query and you may want fastupdate = off.

Trigram (pg_trgm) fuzzy match

tsvector excels at "real words in a real language." It is the wrong tool for typos (postgrres), short codes (SKU-A4F), partial matches (pg_re*), and anything where the stemmer destroys what the user actually typed. For all of those, the pg_trgm extension is the right answer.

Trigrams break a string into overlapping three-character windows — cat becomes {c, ca, cat, at_} — and similarity is the Jaccard overlap between two such sets. The threshold for the % operator defaults to 0.3 and is tunable with pg_trgm.similarity_threshold (or per-session with SET).

Similarity in action

CREATE EXTENSION IF NOT EXISTS pg_trgm;

SELECT similarity('postgresql', 'postgrres') AS sim,
       'postgresql' % 'postgrres'            AS matches;

Result

simmatches
0.583t

The extension also installs operator classes that let GIN and GiST index trigrams, which makes % and ILIKE '%foo%' both index-accelerated. The same index supports both — Postgres extracts trigrams from the ILIKE pattern at plan time.

A trigram GIN index unlocks unanchored ILIKE

CREATE INDEX customers_name_trgm
  ON customers
  USING GIN (name gin_trgm_ops);

SELECT id, name FROM customers WHERE name ILIKE '%berg%';   -- now indexable
SELECT id, name FROM customers WHERE name %  'goldbreg';    -- fuzzy
Pick one Use tsvector for prose; use pg_trgm for identifiers, names, and typo-tolerant lookups. You can index both — they live happily side-by-side on the same table.

When to reach for an external engine

The in-database engine is enough for almost every "search bar on a CRUD app" use case, and the operational saving of not running a second datastore is real. There is, however, a point at which the right answer is Elasticsearch or OpenSearch — and being honest about where it lies is part of using Postgres well.

Reach for an external engine when:

You need per-tenant synonyms or stop words
Postgres configurations are global to a database. Building thousands of configurations for thousands of tenants is possible and miserable.
You need learning-to-rank or BM25 out of the box
ts_rank_cd is fixed-form; you can multiply it by a popularity column and call it a day, but anything model-driven belongs in a system designed for it.
Faceting at scale
"Top 20 brands among matching documents" is one query in ES, an awkward two-step in Postgres.
Many languages in one index
One configuration per language, language-routed at index time, and ES handles it gracefully. In Postgres you end up with per-language columns or per-language tables.
Index size in the hundreds of gigabytes
GIN scales further than people expect, but past a certain point the write amplification and vacuum cost on the indexed table become the dominant operational concern.

For everything else — and most apps live in "everything else" — the in-database engine wins on consistency (the index is always in sync with the row), on operational simplicity (one thing to back up), and on transactional integration (search results respect MVCC, including the writer's own uncommitted changes).
