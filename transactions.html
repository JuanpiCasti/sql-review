Transactions, or, all-or-nothing

A unit of work that either takes effect as a whole or leaves no trace at all. The smallest, most important abstraction Postgres gives you.

A transaction is a sequence of statements that the database treats as one atomic unit. Either every change inside it lands together, or none of them do — there is no partial outcome a concurrent reader can ever observe. In Postgres this is not opt-in: every SQL statement runs inside a transaction. The only question is whether you opened one explicitly or let the server wrap a single statement for you.

The mechanics live behind four verbs — BEGIN, COMMIT, ROLLBACK, SAVEPOINT — but the interesting part is what Postgres guarantees while the transaction is open, and what it refuses to do when something goes wrong inside one.

A note The SQL standard calls it START TRANSACTION; Postgres accepts both. BEGIN is the idiomatic Postgres spelling and the one you will see in production code.

The four verbs

Outside of a transaction block, each statement is implicitly wrapped in its own transaction and committed the moment it returns. Inside a block, statements accumulate and only become visible to other sessions at COMMIT.

A two-statement transfer

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

If the server crashes — or you close your connection — between the two updates, neither one will have happened. A concurrent SELECT reading the same rows will observe either both updates or neither, never one of them.

To discard everything since the BEGIN, use ROLLBACK:

Discarding work in flight

BEGIN;
DELETE FROM orders WHERE created_at < now() - interval '5 years';
-- on reflection, that was too aggressive
ROLLBACK;

The DELETE may have touched millions of rows; after the ROLLBACK, none of them are gone. The MVCC tuples it wrote are dead-on-arrival and will be reclaimed by a future VACUUM.

Idiom Some clients (psql in default mode, JDBC, libpq) commit each statement automatically. Others (psycopg, the asyncpg driver in transaction mode) open a transaction implicitly on the first statement and require you to call commit(). Know which one you're holding.

Aborted transactions

This is the gotcha that catches every newcomer. The instant any statement inside a transaction raises an error, Postgres marks the entire transaction as aborted. Every subsequent statement until you issue ROLLBACK (or ROLLBACK TO a savepoint) is rejected with the same terse message:

The aborted-transaction error

BEGIN;
SELECT * FROM oops;
-- ERROR:  relation "oops" does not exist

SELECT 1;
-- ERROR:  current transaction is aborted,
--         commands ignored until end of transaction block

ROLLBACK;
Pitfall

Unlike MySQL, Postgres will not let you ignore the error and keep going. Once aborted, the only way out is ROLLBACK or ROLLBACK TO <savepoint>. Long-running connection-pool code that "tries and continues" will hang every subsequent query on that connection.

Savepoints — nested rollback

A savepoint is a named marker inside an open transaction. You can ROLLBACK TO it to discard work done after the marker without aborting the whole transaction, or RELEASE it to throw the marker away while keeping the work.

Recovering from a failed insert

BEGIN;
INSERT INTO users (email) VALUES ('ada@example.com');

SAVEPOINT before_optional;
INSERT INTO audit (msg) VALUES ('admitted ada');
-- ERROR:  null value in column "actor" violates not-null constraint

ROLLBACK TO SAVEPOINT before_optional;
-- the users insert is preserved; the audit insert is gone
-- and the transaction is no longer in the aborted state

INSERT INTO audit (actor, msg) VALUES ('system', 'admitted ada');
COMMIT;

Savepoints are how language drivers implement nested transactions: there is no real nesting in Postgres, but a driver can issue a SAVEPOINT sp_42 when you call begin() a second time and ROLLBACK TO sp_42 if that inner block raises.

Cost Savepoints are not free — each one allocates a sub-transaction ID. Loops that take a savepoint per row can exhaust the 32-bit subxid cache (64 per backend) and force every reader to consult pg_subtrans, badly hurting throughput.

Transaction characteristics

You can attach modifiers to a transaction at its start. The two you will actually use:

READ ONLY
Forbids any write (INSERT, UPDATE, DELETE, DDL, SELECT FOR UPDATE). Lets the planner and the WAL machinery take some shortcuts; useful for reporting queries on a replica.
ISOLATION LEVEL
READ COMMITTED (the default), REPEATABLE READ, or SERIALIZABLE. The subject of the next chapter.
DEFERRABLE
Only meaningful for SERIALIZABLE READ ONLY. Tells Postgres it may pause the transaction until it can run without ever causing a serialization failure — useful for long analytic queries.

Setting characteristics

BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;
SELECT count(*) FROM ledger WHERE posted_on = current_date;
COMMIT;

-- or set the default for the session
SET default_transaction_isolation = 'repeatable read';

-- or change just this transaction after BEGIN
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- ...
COMMIT;

Two-phase commit

For distributed transactions across multiple databases, Postgres implements the XA-style two-phase commit protocol. The transaction is first prepared — durably persisted and ready to commit — but not yet visible. A coordinator then commits or rolls back each participant.

Preparing and committing

BEGIN;
UPDATE inventory SET qty = qty - 1 WHERE sku = 'A';
PREPARE TRANSACTION 'order-77-leg-1';
-- session can now disconnect; the prepared tx survives a crash

-- later, from anywhere:
COMMIT PREPARED 'order-77-leg-1';
-- or
ROLLBACK PREPARED 'order-77-leg-1';
Operational warning

Prepared transactions hold locks and prevent VACUUM from advancing the xmin horizon forever until resolved. A crashed coordinator that never sends COMMIT PREPARED leaves you with bloat that grows linearly with write traffic. Always alarm on pg_prepared_xacts. The feature is gated behind max_prepared_transactions = 0 by default for this reason.

What lives outside a transaction

A short, useful list of things you cannot do inside BEGIN ... COMMIT:

  • VACUUM (the whole point is to clean up across many transactions).
  • CREATE INDEX CONCURRENTLY and REINDEX CONCURRENTLY (they manage their own internal transactions in stages).
  • CREATE DATABASE, DROP DATABASE, ALTER SYSTEM.
  • CALLing a procedure that itself contains COMMIT / ROLLBACK.

Conversely, almost everything else is transactional — including DDL. You can BEGIN; ALTER TABLE …; CREATE INDEX …; ROLLBACK; and the schema returns to exactly its prior state. This single property is what makes Postgres migrations so much safer than MySQL's, where most DDL implicitly commits.

Practical Every migration tool worth using wraps each migration in a transaction by default. The exceptions — CREATE INDEX CONCURRENTLY, partition attach/detach with lock waits — must be explicitly marked as non-transactional.

Idle in transaction

A connection that has issued BEGIN but is doing nothing — waiting on application logic, a network round-trip, a user — is in the idle in transaction state. It still holds every lock it has taken and still pins the snapshot it acquired, blocking VACUUM from reclaiming dead tuples newer than its xmin.

You can see them in pg_stat_activity:

Finding long-running idle transactions

SELECT pid,
       usename,
       state,
       now() - xact_start AS xact_age,
       query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND xact_start < now() - interval '5 minutes'
ORDER BY xact_age DESC;

Result

The defence is the GUC idle_in_transaction_session_timeout. Set it to something reasonable (a few minutes) and Postgres will kill the session, releasing locks and unblocking VACUUM:

ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';
SELECT pg_reload_conf();

Transactions, in one card

BEGIN
Open a transaction. Synonym: START TRANSACTION.
COMMIT
Make everything since the BEGIN durable and visible.
ROLLBACK
Discard everything since the BEGIN.
SAVEPOINT n
Place a named marker mid-transaction.
ROLLBACK TO n
Undo only the work after marker n; transaction stays open.
RELEASE n
Drop the marker, keep the work.
PREPARE TRANSACTION
Persist a tx, ready for distributed COMMIT PREPARED.
Aborted state
Any error inside a tx → all further statements rejected until ROLLBACK.
DDL is transactional
You can BEGIN; CREATE TABLE; ROLLBACK; — almost no other database lets you.
Idle-in-tx
Open transactions block VACUUM. Always set idle_in_transaction_session_timeout.
