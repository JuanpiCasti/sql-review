Indexes, or, every shortcut Postgres knows

Five fundamental index types, four ways to modify them, and one rule: the right index for the query you're trying to make fast is rarely the one you'd add by default.

An index is an auxiliary data structure that lets Postgres find rows without scanning the whole table. Every index type — B-tree, Hash, GIN, GiST, SP-GiST, BRIN — answers a different family of questions: equality vs. range vs. containment vs. proximity vs. block-locality. Choosing the wrong type produces an index Postgres won't use; choosing the right one turns a thirty-second sequential scan into a millisecond probe.

B-tree, in detail

The default. Created by every PRIMARY KEY and UNIQUE constraint. A balanced search tree whose leaves are sorted by the indexed key. Supports every operator that can be expressed as an ordering — =, <, <=, >, >=, BETWEEN, IN, and prefix LIKE patterns like 'foo%'.

The composite-key rule

CREATE INDEX ON orders (customer_id, placed_at);

-- supported by the index:
SELECT * FROM orders WHERE customer_id = 1;
SELECT * FROM orders WHERE customer_id = 1 AND placed_at > now() - interval '7 days';
SELECT * FROM orders WHERE customer_id = 1 ORDER BY placed_at DESC LIMIT 10;

-- *not* well supported (the index can't skip ahead on the second column):
SELECT * FROM orders WHERE placed_at > now() - interval '7 days';
-- needs its own index on (placed_at), or a covering composite (placed_at, customer_id).

A composite B-tree on (a, b, c) is useful for queries that filter a, or a and b, or all three — but not for queries that filter only b. Think of the tree as sorted by a first, then b within each a: there's no efficient way to skip over the a dimension.

Equality + range The most useful composite-index recipe: equality columns first, range column last. An index on (status, created_at) serves WHERE status = 'open' AND created_at > X ORDER BY created_at perfectly — the equality narrows, the range walks the leaves in order.

GIN — generalised inverted index

For columns whose values are composite — arrays, JSONB documents, tsvectors — and you want to ask "which rows contain element X?", GIN inverts the storage: one index entry per distinct element, pointing at every row that contains it.

JSONB and array indexes

-- arrays
CREATE INDEX ON posts USING gin (tags);
SELECT * FROM posts WHERE tags @> ARRAY['postgres'];

-- jsonb with the default opclass (jsonb_ops):
--   supports @> ? ?| ?&
CREATE INDEX ON events USING gin (payload);
SELECT * FROM events WHERE payload @> '{"type": "click"}';

-- jsonb with jsonb_path_ops:
--   smaller, faster, but only supports @> (containment)
CREATE INDEX ON events USING gin (payload jsonb_path_ops);

-- full-text
CREATE INDEX ON docs USING gin (to_tsvector('english', body));
SELECT * FROM docs WHERE to_tsvector('english', body) @@ to_tsquery('database & postgres');

GIN indexes are slow to update — adding a row touches every element entry. Postgres ameliorates this with a "pending list" of recent updates that is merged lazily; tune with fastupdate = on (default) and gin_pending_list_limit.

GiST — generalised search tree

A pluggable framework for index types over data with no natural total order: geometric points, ranges, IP networks, full-text rankings. PostGIS lives here. So do range types — and the most underused feature they enable, exclusion constraints:

No two reservations may overlap for the same room

CREATE EXTENSION IF NOT EXISTS btree_gist;  -- to mix scalar and range

CREATE TABLE reservations (
  id          bigserial PRIMARY KEY,
  room_id     int      NOT NULL,
  during      tstzrange NOT NULL,

  EXCLUDE USING gist (
    room_id WITH =,
    during  WITH &&   -- the range overlap operator
  )
);

The constraint is enforced by a GiST index on (room_id, during) using the overlap operator. Any INSERT or UPDATE that would create an overlap fails. There is no application-level race window — the index is the constraint.

BRIN — for big, ordered tables

A BRIN index stores, for each block-range of the table, the minimum and maximum value of the indexed column in that range. A query for created_at > X can skip every range whose max is < X — without storing one index entry per row.

The trade-off: BRIN only helps if the data is physically ordered by the indexed column. On an append-only events table indexed on created_at, a BRIN index a few kilobytes in size can prune 99% of a terabyte-scale table. On a randomly-distributed column, BRIN does nothing for you — every range will have a wide min/max and the scan can skip nothing.

Time-series BRIN

CREATE INDEX ON events USING brin (created_at) WITH (pages_per_range = 128);

Partial indexes

An index with a WHERE clause. The index covers only the rows matching the predicate. Smaller, cheaper to maintain, and often better-suited to skewed data.

Index only the open orders

-- if 95% of orders are 'closed' and you only ever query the open ones:
CREATE INDEX ON orders (placed_at)
WHERE status = 'open';

-- Postgres will use this for:
SELECT * FROM orders WHERE status = 'open' ORDER BY placed_at DESC LIMIT 50;

The planner matches the partial index's WHERE against the query's WHERE. If the query is more restrictive (or equally restrictive) the index is usable. Partial indexes are also the standard way to enforce conditional uniqueness:

CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL;
-- two soft-deleted users may share an email; two live users may not.

Expression indexes

Index a function of a column rather than the column itself. The query must use the exact same expression for the index to apply.

Case-insensitive lookup

CREATE INDEX ON users (lower(email));
SELECT * FROM users WHERE lower(email) = lower('Ada@Example.com');

-- another classic: extracting day from a timestamp
CREATE INDEX ON events (date_trunc('day', created_at));

The expression must be immutable — it must return the same output for the same input forever. now(), random(), and timezone-dependent casts of timestamp all fail this rule and Postgres will refuse the index.

Covering indexes and INCLUDE

A query that can be satisfied entirely from an index — without touching the table heap — is an index-only scan. It's the fastest plan Postgres has. The index must contain every column the query references.

You can append extra payload columns to a B-tree index without making them part of the search key, via INCLUDE:

An INCLUDE-covered query

CREATE INDEX ON orders (customer_id) INCLUDE (placed_at, total);

SELECT placed_at, total
FROM   orders
WHERE  customer_id = 1;
-- can be served as an Index Only Scan: no heap fetches.

Whether Postgres actually uses an index-only scan also depends on the visibility map: rows in pages not marked all-visible still require a heap fetch to check MVCC visibility. VACUUM maintains the visibility map; on a heavily-updated table that hasn't been vacuumed recently, even a perfectly-covered query can degrade to a regular index scan.

CREATE INDEX CONCURRENTLY

Plain CREATE INDEX takes a SHARE lock — blocking all writes for the duration. On a large table that's unacceptable. CREATE INDEX CONCURRENTLY trades a longer build time for non-blocking behaviour: it builds in two scans, allowing concurrent writes throughout.

The production-safe spelling

CREATE INDEX CONCURRENTLY idx_orders_customer ON orders (customer_id);
If it fails

A concurrent build that fails (constraint violation, killed session) leaves an invalid index behind, visible in pg_index.indisvalid = false. The planner won't use it; VACUUM still maintains it. Drop and retry:

DROP INDEX CONCURRENTLY IF EXISTS idx_orders_customer;
CREATE INDEX CONCURRENTLY idx_orders_customer ON orders (customer_id);

Concurrent builds cannot run inside a transaction block — they're driver-of-the-bus statements that manage their own state.

Finding indexes worth dropping

Every index slows down writes and consumes disk. Periodically audit:

Unused and duplicate indexes

-- indexes that have never been scanned since last stats reset
SELECT s.schemaname, s.relname, s.indexrelname,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size,
       s.idx_scan
FROM   pg_stat_user_indexes s
JOIN   pg_index i ON i.indexrelid = s.indexrelid
WHERE  s.idx_scan = 0
  AND  NOT i.indisunique          -- never drop a uniqueness-enforcing index
  AND  NOT i.indisprimary
ORDER  BY pg_relation_size(s.indexrelid) DESC;

Reset the stats counter with pg_stat_reset() at a known point and check again a few weeks later. An index whose idx_scan stays at zero across a full business cycle is a candidate for DROP INDEX CONCURRENTLY.
