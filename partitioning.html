Partitioning, or, when one table isn't enough

A single logical table backed by many physical ones. The planner prunes the partitions it doesn't need; old data drops in a single ALTER TABLE; the application still writes one INSERT.

Past a certain row count, a heap stops being the right shape — vacuum takes forever, indexes are taller than they need to be, and dropping six months of data means a DELETE the size of the moon. Declarative partitioning, added in PG 10 and refined every release since, gives you the operational handles to keep a large table healthy.

Declarative partitioning vs inheritance

Before PG 10, partitioning was a do-it-yourself affair built on top of table inheritance: you created a parent table, a child table for each partition that INHERITS from it, a CHECK constraint on each child describing its slice of the key, and a row-routing trigger on the parent that decoded each INSERT and forwarded it to the right child. The planner used the CHECK constraints to exclude irrelevant children (constraint exclusion), but everything else — routing, attach, detach, foreign-key plumbing — was application code.

Declarative partitioning replaced all of that with one keyword on CREATE TABLE. The parent now knows it is partitioned, the children are declared as PARTITION OF a parent with their bounds inline, and inserts route themselves. The planner uses real partition metadata instead of pattern-matching on CHECK constraints, which is both faster and more honest.

The old way, kept here as a museum piece

CREATE TABLE events (id bigserial, occurred_at timestamptz, payload jsonb);

CREATE TABLE events_2025_01 (
  CHECK (occurred_at >= '2025-01-01' AND occurred_at < '2025-02-01')
) INHERITS (events);

CREATE OR REPLACE FUNCTION events_router() RETURNS trigger AS $$
BEGIN
  IF NEW.occurred_at >= '2025-01-01' AND NEW.occurred_at < '2025-02-01' THEN
    INSERT INTO events_2025_01 VALUES (NEW.*);
  -- ... a branch per month, forever ...
  END IF;
  RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER events_route BEFORE INSERT ON events
  FOR EACH ROW EXECUTE FUNCTION events_router();
Why look back You will still find inheritance-based partitioning in older schemas and in extensions like pg_partman's pre-10 mode. Read it, understand it, and migrate it to declarative — the maintenance cost goes to near zero.

The declarative equivalent is two statements and no triggers. Everything else in this chapter assumes you are on the declarative side.

RANGE, LIST, HASH

A partitioned table has a single partition key — one or more columns, plus a strategy that says how a row's key value maps to a partition. There are three strategies, and the choice is dictated by the shape of the data, not by taste.

RANGE is the workhorse. It carves the key space into ordered, half-open intervals — [low, high) — and is the right answer whenever the key is monotonic: a timestamp, a sequential ID, a version number. Each partition holds a contiguous slice; dropping "everything older than 12 months" becomes a single DETACH.

A monthly events table

CREATE TABLE events (
  id          bigint  GENERATED ALWAYS AS IDENTITY,
  occurred_at timestamptz NOT NULL,
  payload     jsonb,
  PRIMARY KEY (id, occurred_at)        -- must include the partition key
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2025_01 PARTITION OF events
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

CREATE TABLE events_2025_02 PARTITION OF events
  FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

LIST partitions by an explicit set of discrete values per child. Think region codes, tenant IDs, status enums — anything where there is no "between," only "in this set or that one." It is the strategy used most often for multi-tenant tables where each large customer gets its own partition and the long tail shares a default.

Customers split by region

CREATE TABLE customers (
  id      bigint GENERATED ALWAYS AS IDENTITY,
  region  text   NOT NULL,
  email   text,
  PRIMARY KEY (id, region)
) PARTITION BY LIST (region);

CREATE TABLE customers_eu PARTITION OF customers FOR VALUES IN ('DE','FR','ES','IT');
CREATE TABLE customers_us PARTITION OF customers FOR VALUES IN ('US','CA');
CREATE TABLE customers_other PARTITION OF customers DEFAULT;

HASH is what you reach for when there is no natural slicing key — only the need to spread write load evenly across N children. Postgres hashes the key with a deterministic function and assigns the row to hash mod N. You give up range pruning (no WHERE id BETWEEN … can skip partitions) in exchange for an even distribution.

An audit log spread across eight partitions

CREATE TABLE audit_log (
  id       bigint GENERATED ALWAYS AS IDENTITY,
  actor_id bigint NOT NULL,
  at       timestamptz NOT NULL DEFAULT now(),
  detail   jsonb,
  PRIMARY KEY (id, actor_id)
) PARTITION BY HASH (actor_id);

CREATE TABLE audit_log_0 PARTITION OF audit_log FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE audit_log_1 PARTITION OF audit_log FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ... through REMAINDER 7

You can compose strategies — a RANGE-partitioned table whose children are themselves HASH-partitioned is a common pattern for very large time-series with hot recent buckets. The composition is implemented exactly as it reads: each child is a partitioned table in its own right.

Partition pruning and the planner

Partition pruning is the optimisation that makes the whole feature pay off. When the planner can prove from the WHERE clause that a partition cannot contain any matching rows, it skips that partition entirely — no scan, no lock, no presence in the plan tree. On a thousand-partition table, a well-pruned query reads from one child.

Pruning fires only on conditions over the partition key. A filter on any other column reaches every partition, because the planner has no way to know which children it lives in. This is the single most important thing to internalise about partitioning: the key choice is the query plan.

A pruned plan touches one child

EXPLAIN SELECT count(*) FROM events
WHERE occurred_at >= '2025-02-10' AND occurred_at < '2025-02-11';

                            QUERY PLAN
-------------------------------------------------------------------
 Aggregate
   ->  Seq Scan on events_2025_02 events
         Filter: (occurred_at >= '2025-02-10' AND occurred_at < '2025-02-11')

Compare to the same query with a non-key filter, where every partition appears in the plan:

A filter on a non-key column hits every child

EXPLAIN SELECT count(*) FROM events WHERE payload->>'type' = 'signup';

                                QUERY PLAN
---------------------------------------------------------------------------
 Aggregate
   ->  Append
         ->  Seq Scan on events_2025_01 events_1
         ->  Seq Scan on events_2025_02 events_2
         ->  Seq Scan on events_2025_03 events_3
         ->  ... one branch per partition ...

Pruning happens both at plan time (when the bounds are known from constant literals) and at execution time (when they come from a parameterised prepared statement or a join). The latter is why an EXPLAIN may show all partitions in the plan tree while EXPLAIN ANALYZE reports Partitions removed: 11 for the actual run.

Note

The toggle is enable_partition_pruning (on by default). The older constraint_exclusion GUC controls inheritance-style pruning only and is mostly irrelevant on modern declarative tables — leave it at partition.

Attaching and detaching without long locks

Bringing a new partition into a table looks innocuous — ALTER TABLE … ATTACH PARTITION … — but it takes an ACCESS EXCLUSIVE lock on the parent and scans the entire candidate child to verify that every row satisfies the partition's bounds. On a hot OLTP table with a 200 GB candidate, both of those are unacceptable in production.

The workaround is to give Postgres proof, ahead of time, that the scan is unnecessary. Add a CHECK constraint matching the future partition's bounds, then attach — the planner sees the matching constraint and skips the scan. The lock on the parent is still ACCESS EXCLUSIVE, but it is now held only for the moment it takes to update the catalog.

Attach without the long scan

-- 1. Build the new partition as a standalone table.
CREATE TABLE events_2025_03 (LIKE events INCLUDING ALL);

-- 2. Load it (COPY, INSERT … SELECT, whatever).
\copy events_2025_03 FROM 'march.csv' WITH (FORMAT csv)

-- 3. Pre-validate with a CHECK matching the bounds.
ALTER TABLE events_2025_03
  ADD CONSTRAINT events_2025_03_range
  CHECK (occurred_at >= '2025-03-01' AND occurred_at < '2025-04-01') NOT VALID;
ALTER TABLE events_2025_03 VALIDATE CONSTRAINT events_2025_03_range;

-- 4. Attach. No table scan; lock held only briefly.
ALTER TABLE events
  ATTACH PARTITION events_2025_03
  FOR VALUES FROM ('2025-03-01') TO ('2025-04-01');

-- 5. The redundant CHECK can now be dropped.
ALTER TABLE events_2025_03 DROP CONSTRAINT events_2025_03_range;

Detach is the symmetrical operation, and the unqualified form has the same problem: ALTER TABLE … DETACH PARTITION takes ACCESS EXCLUSIVE on the parent. PG 14 introduced DETACH PARTITION … CONCURRENTLY, which runs in two steps with weaker locks — first marks the partition as detaching (only blocks new queries that would attempt pruning against it), then finalises after existing transactions drain. It is how you drop old data without an outage window.

Dropping last year's data

ALTER TABLE events DETACH PARTITION events_2024_03 CONCURRENTLY;
DROP TABLE events_2024_03;
Cannot run inside a transaction DETACH PARTITION CONCURRENTLY is one of the small set of statements that cannot run inside BEGIN … COMMIT, alongside CREATE INDEX CONCURRENTLY. Your migration tool needs to mark the step as non-transactional.

Default partitions and partition-wise joins

A default partition catches every row that does not match any other partition's bounds. It is useful as a safety net during a rollout — better than a constraint violation — and as the long-tail bucket for LIST partitioning where you only want explicit partitions for the largest tenants.

The catch is that adding a new partition to a table that already has a default requires Postgres to scan the default and prove that none of its rows belong in the new bounds. That scan runs under an ACCESS EXCLUSIVE lock on the default partition. On a populated default, the wait can be long; the mitigation is the same CHECK-then-attach pattern from the previous section, applied to the default itself.

Operational warning

A default partition that has filled up with millions of rows because nobody created the next month's partition on time is a classic incident. Alert on default-partition row counts; better, automate the partition rollover with pg_partman or a scheduled function.

Partition-wise joins are the planner's reward for partitioning two tables on the same key with matching bounds. With enable_partitionwise_join on, the planner joins each pair of corresponding partitions independently — twelve smaller hash joins instead of one large one — and the same for aggregates under enable_partitionwise_aggregate. Both are off by default because the planner cost of considering them is non-trivial; turn them on when you have wide partitioned tables joined in the hot path.

Turning the optimisations on

SET enable_partitionwise_join = on;
SET enable_partitionwise_aggregate = on;

Pitfalls — no global indexes, UNIQUE must include the partition key

Postgres has no global indexes across partitions. Every index lives on exactly one partition; an "index on the parent" is shorthand for "an index template that Postgres propagates to each child." This has two consequences that bite newcomers.

First, every UNIQUE or PRIMARY KEY constraint on a partitioned table must include the partition key. There is no other way for Postgres to enforce uniqueness without scanning every partition on every insert — and the design refuses to do that. If your application logic needs a column to be globally unique, the partition key is forced to either be that column or be derivable from it.

Why a bare email PK fails

CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY,
  email text UNIQUE,                       -- ✗
  region text NOT NULL
) PARTITION BY LIST (region);

-- ERROR:  unique constraint on partitioned table must include all
--         partitioning columns
-- DETAIL: UNIQUE constraint on table "users" lacks column "region"
Pitfall

The workaround is some combination of: (a) include the partition key in the PK (PRIMARY KEY (email, region)), at the cost of allowing duplicates across regions; (b) maintain a non-partitioned dedup table (users_email (email PK, user_id)) and enforce uniqueness in application code via an insert into both tables in the same transaction; or (c) reconsider whether the table needs partitioning at all. There is no fourth option.

Second, foreign keys referencing a partitioned table only work from PG 12 onward, and the cascade machinery has to fan out across every partition — on a partitioned parent with hundreds of children, a DELETE CASCADE can be surprisingly expensive. Foreign keys from a partitioned table to a non-partitioned one are unremarkable and cheap.

Concurrent indexes CREATE INDEX on a partitioned table is non-concurrent in the same way ATTACH PARTITION is — it locks each child while building. The pattern is to build the index on each partition with CREATE INDEX CONCURRENTLY separately, then run CREATE INDEX ON parent (…) ONLY followed by ALTER INDEX … ATTACH PARTITION … per child.

Partitioning, in one card

PARTITION BY RANGE
Time series, monotonic IDs. The most common choice.
PARTITION BY LIST
Discrete keys: region, tenant, status.
PARTITION BY HASH
Spread writes evenly when no natural key exists.
Partition pruning
Planner skips partitions whose constraint excludes the WHERE. Only triggers on the partition key.
ATTACH PARTITION
Bring a pre-loaded table in. Use CONCURRENTLY-equivalent patterns to avoid the ACCESS EXCLUSIVE lock.
DETACH PARTITION CONCURRENTLY
The clean way to drop old data.
Default partition
Catches anything that doesn't match. Adding new partitions locks the default.
Global indexes
Don't exist. Every index is per-partition.
UNIQUE / PRIMARY KEY
Must include the partition key. Non-negotiable.
Foreign keys
You can reference a partitioned table (PG 12+). Cascades can be slow.
