Joins, or, putting tables together

Every way Postgres lets you combine two relations: inner, the four outer flavours, cross, lateral, and the two implicit kinds — semi and anti — you write with EXISTS.

A join takes two tables and produces a third whose rows are formed from pairs of input rows that satisfy some condition. Almost every interesting SQL query is a join in disguise — even the ones written with IN, EXISTS, or scalar subqueries. Learning the algebra explicitly means you can write the same query four different ways and know which one the planner will run fastest.

Sample schema Throughout this chapter: authors(id, name) with three rows, books(id, author_id, title) with four rows — one author has no book, one book has no author (NULL author_id).

§ 4.1 The five named joins, at a glance

INNER
matches in both
LEFT
all left, matched right
RIGHT
all right, matched left
FULL OUTER
all rows on either side
CROSS
every pair (cartesian)

Outer joins fill in NULL for columns from the side that had no match. Inner joins drop unmatched rows. Cross joins ignore matching entirely — they produce |L| × |R| rows.

§ 4.2 INNER JOIN

Ex. 4.1 Books with their author

SELECT b.title, a.name AS author
FROM   books b
JOIN   authors a ON a.id = b.author_id
ORDER  BY b.id;

Result — the book with NULL author_id and the author with no books are both gone

The bare keyword JOIN always means INNER JOIN. The two are interchangeable — write whichever is clearer in context. (I prefer the explicit INNER when the same query also has outer joins, for visual symmetry.)

§ 4.3 LEFT JOIN (and its mirror)

Ex. 4.2 Every author, with their books if any

SELECT a.name, b.title
FROM   authors a
LEFT   JOIN books b
  ON   b.author_id = a.id
ORDER  BY a.name, b.id;

Sappho appears with a NULL title — she's preserved by the LEFT, then her unmatched right-hand columns are filled with nulls. The book with NULL author_id is still absent: only the left side is preserved.

RIGHT JOIN is identical with the sides reversed. By convention, write everything as LEFT JOIN and reorder the tables — it's the same query, and one direction of asymmetry is easier to read.

§ 4.4 FULL OUTER JOIN

Ex. 4.3 Everything from both sides

SELECT a.name, b.title
FROM   authors a
FULL   OUTER JOIN books b
  ON   b.author_id = a.id;

Sappho (unmatched author) and the anonymous book (unmatched book) both appear, each with nulls on the opposing side. FULL OUTER is rare in OLTP but invaluable for reconciliation queries — diffing two snapshots of the same data.

§ 4.5 CROSS JOIN

Every row of the left side paired with every row of the right side, with no condition. Three authors × four books = twelve rows. Usually a mistake — but occasionally exactly what you want:

Ex. 4.4 Generating a date×product matrix

SELECT d::date, p.id
FROM   generate_series(date '2026-01-01', date '2026-01-07', interval '1 day') d
CROSS  JOIN products p
ORDER  BY d, p.id;

The classic use: ensure a report has a row for every (date, dimension) combination even when there were no events, then LEFT JOIN the events onto it.

Two equivalent spellings: FROM a, b (the old comma syntax) and FROM a CROSS JOIN b are the same query. Prefer the explicit form so a missing WHERE clause doesn't silently produce a cartesian product.

§ 4.6 ON vs USING vs NATURAL

Three ways to write the join condition:

ON expr
Arbitrary predicate. The general case.
USING (cols)
Shortcut for ON a.c = b.c when both sides have a column named c. The result has one column c, not two — useful when you'd otherwise SELECT *.
NATURAL JOIN
Implicit USING on every column with a shared name. Don't. A future ALTER TABLE ADD COLUMN on either side can silently change the join condition.

Ex. 4.5 USING tidies up self-explanatory keys

SELECT * FROM orders JOIN order_items USING (order_id);
-- one order_id column in the output, plus everything else from both tables

§ 4.7 LATERAL — the correlated subquery in FROM

A LATERAL join lets a subquery on the right side reference columns from the left side. Without LATERAL, the items in a FROM clause are independent of each other; with it, the right side is evaluated once per row of the left.

The canonical use is top-N per group:

Ex. 4.6 Two most recent orders per customer

SELECT c.id, c.name, o.placed_at, o.total
FROM   customers c
JOIN   LATERAL (
         SELECT placed_at, total
         FROM   orders
         WHERE  customer_id = c.id    -- references the outer c.id
         ORDER  BY placed_at DESC
         LIMIT  2
       ) o ON true
ORDER  BY c.id;

Without LATERAL the inner WHERE customer_id = c.id would be illegal — the subquery cannot see c. With it, you get exactly the rows you want with a single pass, and on a well-indexed orders(customer_id, placed_at DESC) the planner can serve each customer's two rows from the index directly.

When to prefer LATERAL over window functions

The same top-N can be expressed with ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY placed_at DESC). The window-function version scans all orders and ranks them; LATERAL with LIMIT probes the index per customer. For small N and many groups, LATERAL usually wins by a large margin.

§ 4.8 Semi-joins and anti-joins

A semi-join returns rows of the left side that have at least one match on the right — but without multiplying rows the way an inner join would. Postgres recognises three idioms for this, all producing the same plan:

Ex. 4.7 Authors who have written at least one book

-- semi-join, the canonical spelling
SELECT * FROM authors a
WHERE  EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id);

-- equivalent, but easier to get wrong (see § 4.9)
SELECT * FROM authors WHERE id IN (SELECT author_id FROM books);

-- a INNER JOIN with DISTINCT can also express this, but the planner
-- usually rewrites EXISTS / IN into a "Semi Join" node directly.

An anti-join is the negation: rows of the left with no match on the right. NOT EXISTS is the safe spelling:

Ex. 4.8 Authors with no book

SELECT * FROM authors a
WHERE  NOT EXISTS (
  SELECT 1 FROM books b WHERE b.author_id = a.id
);

-- another spelling, often produces the same plan:
SELECT a.*
FROM   authors a
LEFT   JOIN books b ON b.author_id = a.id
WHERE  b.id IS NULL;

§ 4.9 The NOT IN NULL trap

This is the single nastiest bug in SQL semantics. If the subquery in NOT IN returns even one NULL, the entire outer query returns no rows:

Ex. 4.9 The trap, and the fix

-- books table contains one row with author_id = NULL

-- "authors who have no book" — looks right, returns ZERO rows
SELECT * FROM authors
WHERE  id NOT IN (SELECT author_id FROM books);

-- the fix: NOT EXISTS, which handles NULLs correctly
SELECT * FROM authors a
WHERE  NOT EXISTS (SELECT 1 FROM books b WHERE b.author_id = a.id);

Why? x NOT IN (1, 2, NULL) evaluates to x <> 1 AND x <> 2 AND x <> NULL. The last clause is NULL (three-valued logic: "unknown"), which makes the whole conjunction at best NULL — never true. The outer WHERE drops anything that isn't true.

Rule of thumb

Use NOT EXISTS for anti-joins. Reserve NOT IN for fixed literal lists you wrote yourself, where you know nothing can be NULL.

§ 4.10 Self-joins

A table joined to itself — typically with two aliases. Useful for hierarchies (parent/child), pairwise comparisons, and gap-filling.

Ex. 4.10 Employee → manager lookup

SELECT e.name AS employee, m.name AS manager
FROM   employees e
LEFT   JOIN employees m ON m.id = e.manager_id;

The LEFT ensures the CEO (whose manager_id is null) still appears, with a null manager.

§ 4.11 Join order, theta-joins, and the planner

The order you write join clauses in is almost never the order Postgres executes them. The planner enumerates join orders and picks the cheapest by its cost model — capped by join_collapse_limit (default 8). Beyond that limit it falls back to the order you wrote.

Two terms worth knowing:

Equi-join
Join condition uses only =. Eligible for hash and merge joins; cheap.
Theta-join
Any other operator (<, >, BETWEEN, range overlap). Restricted to nested-loop or merge with a range strategy; expensive.

Range-overlap joins on time intervals are the classic theta-join — they often need a custom index (GiST on a range type) or a query rewrite to be tractable.

Joins, in one card

INNER
Matches in both sides. Default for bare JOIN.
LEFT
All left rows; right columns null when unmatched.
FULL OUTER
Both sides preserved; nulls fill in.
CROSS
Cartesian product. No condition.
LATERAL
Right side may reference left columns. Top-N-per-group's best friend.
EXISTS
Semi-join. One row per match-having left row.
NOT EXISTS
Anti-join. The safe spelling.
NOT IN
Broken on NULLs. Use only with literal lists.
USING (col)
Shortcut for equi-join; merges the column in the result.
NATURAL JOIN
Don't.
join_collapse_limit
Cap on planner join-order search. Default 8.
