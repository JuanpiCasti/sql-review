CTEs & recursion

The WITH clause turns a query into a script — named, ordered intermediate results that can reference each other, recurse on themselves, and even modify data.

A common table expression is a named subquery written before the main query. It exists for one statement, evaluates to a temporary relation, and can be referenced wherever a table can. Used for clarity, it splits a tangled query into named steps you can read top-to-bottom. Used recursively, it does things plain SQL cannot — tree walks, graph traversals, generating sequences. Used with INSERT, UPDATE, or DELETE, it captures the rows you just changed for use in the next step.

§ 7.1 Basic WITH

Ex. 7.1 A query as a script

WITH recent_orders AS (
  SELECT * FROM orders
  WHERE placed_at >= now() - interval '30 days'
),
order_totals AS (
  SELECT customer_id, sum(total) AS total
  FROM   recent_orders
  GROUP  BY customer_id
)
SELECT c.name, ot.total
FROM   customers c
JOIN   order_totals ot ON ot.customer_id = c.id
ORDER  BY ot.total DESC
LIMIT  20;

Two CTEs, each referenced once. Note that order_totals references recent_orders by name — later CTEs in the same WITH may use earlier ones; the reverse is not allowed.

CTEs are scoped to the single statement they belong to. They are not views — they leave no trace after the statement ends and they don't appear in pg_class.

Worth noting For most queries you can replace any CTE with a subquery in the FROM clause and get an identical plan. Use CTEs when the resulting query is meaningfully easier to read top-to-bottom.

§ 7.2 MATERIALIZED — the Postgres 12 change

Before Postgres 12, every CTE was an optimisation fence: the planner ran each CTE to completion, stored its rows in a working table, and the outer query read from that table. Predicates could not push into a CTE; statistics from the inner query could not be used outside. This made CTEs slower than equivalent subqueries in most cases.

Postgres 12 changed the default. A CTE that is referenced exactly once and is not recursive and has no side effects is now inlined — treated as if you'd written it as a subquery, with predicate push-down and join-order freedom. CTEs that are referenced multiple times still default to materialised, because re-evaluating them might cost more than caching.

Two keywords let you force the choice:

WITH x AS MATERIALIZED (...)
Always materialise. Same behaviour as pre-12.
WITH x AS NOT MATERIALIZED (...)
Always inline (when safe).

Ex. 7.2 Forcing materialisation as an optimisation barrier

-- Useful when an expensive aggregation is referenced many times,
-- or when you genuinely want the planner to compute the CTE first.
WITH stats AS MATERIALIZED (
  SELECT region, percentile_cont(0.95) WITHIN GROUP (ORDER BY latency) AS p95
  FROM   requests
  GROUP  BY region
)
SELECT r.*, s.p95
FROM   requests r
JOIN   stats s USING (region)
WHERE  r.latency > s.p95;
When to MATERIALIZE explicitly

(1) A CTE used several times whose inputs change between references (rare but possible with volatile functions). (2) A CTE you want to debug — materialising it forces the planner to actually compute that step so you can inspect it via EXPLAIN ANALYZE. (3) A correctness-critical optimisation fence (e.g. you must read consistent state before writing).

§ 7.3 Recursive CTEs

A WITH RECURSIVE clause defines a relation in terms of itself. The body is two SELECTs connected by UNION ALL (or UNION for deduplication): the anchor (non-recursive) and the recursive term, which references the CTE name.

Execution: evaluate the anchor; while the recursive term, applied to the latest batch of rows, produces new rows, keep going. Stop when it produces none.

Ex. 7.3 Walking a tree of categories

WITH RECURSIVE descendants AS (
    -- anchor: start from the root we care about
    SELECT id, parent_id, name, 0 AS depth, ARRAY[id] AS path
    FROM   categories
    WHERE  id = 1

  UNION ALL

    -- recursive: children of the current frontier
    SELECT c.id, c.parent_id, c.name, d.depth + 1, d.path || c.id
    FROM   categories c
    JOIN   descendants d ON c.parent_id = d.id
)
SELECT repeat('  ', depth) || name AS tree, depth
FROM   descendants
ORDER  BY path;

The depth and path columns are typical recursion bookkeeping: depth for pretty-printing, path to detect cycles and to give a stable ordering.

Cycle protection

If the data forms a cycle and you use UNION ALL, the CTE will recurse forever. Defences: (1) use UNION instead, which deduplicates; (2) track the path explicitly and add WHERE NOT (c.id = ANY(d.path)); (3) use the standard CYCLE clause introduced in Postgres 14, which adds a flag column and prunes automatically.

§ 7.4 The SEARCH and CYCLE clauses (PG 14+)

Two standard clauses that recursive CTEs may carry, both added in Postgres 14.

Ex. 7.4 SEARCH and CYCLE in one query

WITH RECURSIVE descendants AS (
    SELECT id, parent_id, name FROM categories WHERE id = 1
  UNION ALL
    SELECT c.id, c.parent_id, c.name
    FROM   categories c JOIN descendants d ON c.parent_id = d.id
)
SEARCH DEPTH FIRST BY id SET ordering   -- adds an "ordering" column
CYCLE id SET is_cycle USING cycle_path  -- adds is_cycle bool + cycle_path array
SELECT id, name, ordering, is_cycle
FROM   descendants
ORDER  BY ordering;

SEARCH chooses depth-first or breadth-first ordering. CYCLE stops infinite recursion safely. Both are syntactic sugar over the manual bookkeeping in § 7.3, but a much nicer one to read.

§ 7.5 Generating sequences without a table

A favourite use of WITH RECURSIVE: produce a series of rows out of thin air. (For numbers, generate_series is simpler — but the pattern generalises.)

Ex. 7.5 Fibonacci, in SQL

WITH RECURSIVE fib(i, a, b) AS (
    VALUES (1::bigint, 0::bigint, 1::bigint)
  UNION ALL
    SELECT i + 1, b, a + b FROM fib WHERE i < 20
)
SELECT i, a AS fib FROM fib;

§ 7.6 Data-modifying CTEs

Postgres lets INSERT, UPDATE, DELETE, and MERGE appear inside a WITH clause, provided they use RETURNING. The returned rows are visible to the rest of the statement — useful for "do A, then do B with the keys A produced":

Ex. 7.6 Move rows from one table to another, atomically

WITH moved AS (
  DELETE FROM staging
  WHERE   ready = true
  RETURNING id, payload, created_at
)
INSERT INTO events (id, payload, created_at, archived_at)
SELECT id, payload, created_at, now()
FROM   moved
RETURNING id;

The delete and insert run in the same statement under the same transaction; either both succeed or neither does. There is no window in which the rows are missing from both tables, or duplicated across them.

A subtle rule

Sub-statements in a data-modifying CTE all see the same snapshot — the snapshot at the start of the outer statement. A SELECT CTE that reads from a table modified by a sibling UPDATE CTE will not see the update. If you depend on the new values, read them via RETURNING, not by re-querying the table.

§ 7.7 When not to use a CTE

Two situations where a subquery in the FROM clause is the better tool:

  • Trivial reuse. A CTE used in one place adds a name; if the name doesn't help readability, just inline the subquery.
  • Tight predicate push-down matters. Even with PG 12 inlining, a WITH reads more like a barrier than a subquery does. When you want the planner to think of the whole thing as one query, write it as one.

And one place a CTE is the only option: when you need to reference an intermediate result multiple times and recomputing would change the answer — e.g. when computing percentiles or random samples.
