MVCC & VACUUM, or, the immortal row

Postgres never updates a row in place. Every change writes a new tuple; every delete merely marks the old one. The machinery that decides which version you see — and which long-dead ones can finally be erased — is MVCC.

Multi-version concurrency control is the trick that lets Postgres deliver snapshot isolation without making readers wait for writers. Each row in a table is really a chain of physical tuples, stamped with the transaction IDs that created and (eventually) deleted them. A query's snapshot picks exactly one version of each row to be visible. Old versions are not freed when their transaction ends — they are freed by VACUUM, on its own schedule, once no live snapshot can still need them.

xmin, xmax, and the tuple header

Every tuple stored on disk carries a small header. The two fields that matter for visibility are:

xmin
The transaction ID that inserted this version of the row.
xmax
The transaction ID that deleted (or replaced) this version. Zero if the version is still live.
ctid
The physical address — (block, offset) — of this tuple. Updates write a new tuple and leave the old one pointing at it via ctid, forming an update chain.

These are real system columns. You can select them like any other:

Inspecting tuple versions

CREATE TABLE t (id int, val text);
INSERT INTO t VALUES (1, 'first');
UPDATE t SET val = 'second' WHERE id = 1;

SELECT ctid, xmin, xmax, * FROM t;

Result (live tuple only — the older one is dead)

ctidxminxmaxidval
(0,2)74801second

The tuple at (0,1) still exists on disk, with xmin=747, xmax=748, but it isn't visible to your snapshot. It's dead — waiting for VACUUM.

Why this matters The fact that UPDATE writes a new tuple is why heavily-updated tables bloat, why HOT updates are a big win, and why an index on a column you never query can still slow your writes down.

Snapshots and visibility

When a transaction takes a snapshot it captures three things: the current transaction ID counter (xmax of the snapshot), the oldest still-running transaction (xmin), and the list of in-progress transaction IDs in between (xip).

A tuple is visible to that snapshot if, roughly:

  • Its xmin is less than the snapshot's xmax, and not in the in-progress list, and committed; and
  • Its xmax is zero, or aborted, or still in the in-progress list, or greater than the snapshot's xmax.

You never write this logic yourself. But it's the reason a long-running SELECT at Repeatable Read can still see a row that was deleted ten minutes ago: that row's xmax is committed, but it's greater than the snapshot's xmax, so to the snapshot the delete hasn't happened yet.

HOT updates

An ordinary UPDATE must update every index on the table, because the new tuple lives at a new ctid and every index entry points to a ctid. This is expensive — on a table with ten indexes, ten index writes per row update.

The HOT (Heap-Only Tuple) optimisation avoids this if two conditions hold:

  • No indexed column is changed by the update.
  • The new tuple fits on the same heap page as the old one.

When both are true, Postgres writes the new tuple on the same page, links it from the old one with an HOT chain, and does not touch any index. Index entries still point at the old ctid; the page-level chain hops them forward to the live version. HOT can also be cleaned up by routine page-level "mini-vacuums" called HOT pruning, which run opportunistically during normal operations.

In practice

This is why leaving a little free space on each heap page matters. The storage parameter fillfactor (default 100) controls how packed each new page is. For update-heavy tables, dropping fillfactor to 80–90 dramatically increases the HOT-update rate.

Dead tuples, bloat, and VACUUM

A tuple is dead when no current or future snapshot can see it — i.e. its xmax committed, and the oldest snapshot's xmin is past that commit. Until VACUUM runs, dead tuples occupy disk space, get scanned by sequential scans, and accumulate in indexes.

VACUUM does three things:

  1. Marks dead tuples' line pointers as reusable so future inserts can overwrite them.
  2. Removes corresponding entries from every index on the table.
  3. Updates the table's visibility map and free space map, and advances the relation's relfrozenxid to prevent transaction-ID wraparound.

It does not return disk space to the OS. The pages stay allocated, just with reusable holes. To physically shrink a table you need VACUUM FULL (which rewrites the whole table under an AccessExclusive lock — never run it on a live OLTP table) or pg_repack (which does the same online).

The horizon

VACUUM can only remove tuples older than the oldest snapshot currently in use, anywhere. One forgotten idle in transaction session, one stuck replication slot, one abandoned PREPARE TRANSACTION, and your VACUUM does nothing — your tables grow without bound while VACUUM completes successfully every run. The blocker query later in this chapter is how you find it.

Autovacuum

You don't run VACUUM by hand. The autovacuum launcher runs in the background and triggers a vacuum on a table when its dead-tuple count crosses a threshold:

threshold = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × n_live_tuples

Defaults are 50 + 0.2 × rows — i.e. fire when dead tuples exceed 20% of the live row count. For a 100M-row table this is far too slack; tune the per-table storage parameters down:

Tuning autovacuum per table

ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.02,   -- 2% instead of 20%
  autovacuum_vacuum_threshold    = 1000,
  autovacuum_analyze_scale_factor = 0.01
);

Autovacuum also runs an ANALYZE (to refresh planner statistics) on its own threshold, and a periodic anti-wraparound VACUUM FREEZE that you cannot defer.

Finding what blocks VACUUM

One query that earns its keep. The backend_xmin column of pg_stat_activity shows the oldest transaction ID still needed by each session. The lowest value across the cluster is the horizon below which VACUUM cannot reclaim:

The VACUUM horizon

SELECT pid,
       usename,
       state,
       now() - xact_start  AS xact_age,
       backend_xmin,
       query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC
LIMIT 10;

-- and for replication slots:
SELECT slot_name, active, xmin, catalog_xmin,
       age(xmin) AS xmin_age
FROM pg_replication_slots
ORDER BY age(xmin) DESC NULLS LAST;

Wraparound

Transaction IDs are 32-bit. After ~2 billion transactions, they wrap. Postgres protects against this by periodically freezing old tuples — replacing their xmin with a sentinel that means "always visible". Freezing happens during VACUUM, and is triggered no later than vacuum_freeze_table_age (default 150M) since the table was last frozen.

If freezing falls so far behind that wraparound becomes imminent, Postgres will refuse new transactions:

ERROR: database is not accepting commands to avoid wraparound data loss in database "x"

This is recoverable but humiliating. Monitor age(datfrozenxid) per database; alarm at half of autovacuum_freeze_max_age (default 200M).

PG 17+ Recent Postgres versions add 64-bit transaction-ID tracking in some catalogs and improvements to freeze efficiency, but the 32-bit on-disk xid remains. Wraparound monitoring is still load-bearing.

MVCC, in one card

xmin / xmax
Inserting / deleting transaction ID stamped on each tuple version.
ctid
Physical (block, offset) of a tuple. Update chains link old → new.
Snapshot
(xmin, xmax, xip) triple. Visibility is purely a function of these vs the tuple's stamps.
HOT update
Update that touches no indexed column and fits on the same page → skips all index writes.
fillfactor
Drop to 80–90 on update-heavy tables to make HOT updates likely.
VACUUM
Reclaims dead tuples, updates visibility/free-space maps, advances relfrozenxid.
VACUUM FULL
Rewrites the table. Takes AccessExclusive. Don't. Use pg_repack.
backend_xmin
The oldest tx ID a session still needs. The minimum across the cluster is the VACUUM horizon.
Wraparound
32-bit xids. Monitor age(datfrozenxid); freeze before wraparound forces a shutdown.
