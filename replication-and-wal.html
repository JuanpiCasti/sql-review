Replication & WAL, or, durability past the disk

A log of every change the server has ever made, streamed to a hot standby, replayed on failover, and archived for point-in-time recovery.

Every committed write in Postgres lands in the write-ahead log before it touches the heap. That log is what makes crash recovery work — and it's the substrate every form of replication is built on. This chapter is the durability story from disk to standby to off-site archive.

What WAL is and how it gets written

Before Postgres modifies a single heap page on disk, it writes a record describing the change to an append-only file in pg_wal/. Only after that record is durably persisted is the in-memory page change considered safe. This is the write-ahead log, and it is the keystone of every durability and replication feature in the system: crash recovery, streaming replication, logical replication, PITR — all of them are different ways of reading the same log.

The log is a sequence of fixed-size segments (16 MB by default), and every byte in it has a monotonically increasing position called the LSN — log sequence number, printed as 0/1A3F2C8. The LSN is the universal coordinate of "where in time" the cluster is. pg_current_wal_lsn() on the primary and pg_last_wal_replay_lsn() on a standby are the most useful single readings.

Where the log is, and where it's at

SELECT pg_current_wal_lsn()              AS current_lsn,
       pg_walfile_name(pg_current_wal_lsn()) AS current_segment;

Result

current_lsncurrent_segment
0/1A3F2C8000000010000000000000001

The write path: a backend appends WAL records to wal_buffers in shared memory. At COMMIT, the backend calls XLogFlush, which writes and fsyncs all buffered WAL up to and including its own commit record. Only then does COMMIT return to the client. A crash before the fsync loses the transaction; a crash after it does not.

Crash recovery is the symmetric operation. On startup, Postgres locates the most recent checkpoint in WAL, replays every record from there forward, and the cluster comes up at the LSN of the last durable record. Nothing committed is ever lost; nothing uncommitted is ever applied.

fsync is real fsync = off exists. It makes writes vastly faster and makes durability a fiction — a power loss can corrupt the cluster beyond repair. Use it only on throwaway test databases.

Physical replication — streaming, replication slots

Streaming replication is the simplest replica shape Postgres offers: a standby connects to the primary, requests WAL starting at a particular LSN, and applies the records byte-for-byte. The standby is a binary clone — same Postgres version, same architecture, same on-disk layout. Read-only queries against it (hot standby) see exactly the data the primary saw a moment ago, minus replication lag.

Bringing up a standby — the broad strokes

# 1. Base backup of the primary into the standby's data directory.
pg_basebackup -h primary.internal -U replicator -D /var/lib/postgres/data -R

# 2. The -R flag wrote standby.signal and primary_conninfo into
#    postgresql.auto.conf for us. Start the server.
pg_ctl -D /var/lib/postgres/data start

The key piece on the primary is the replication slot. A slot is a server-side bookmark that records the oldest LSN any consumer (standby, logical subscriber, backup tool) still needs. As long as a slot exists, Postgres refuses to delete WAL segments past the slot's position — which is exactly what you want when a standby goes offline and reconnects an hour later.

Slots in use

Operational warning

The third row is what kills clusters. A slot that no consumer is reading from never advances, and the WAL it pins grows without bound until pg_wal/ fills the disk and the primary refuses writes. Alert on pg_replication_slots with active = false and on retained_bytes over a sane threshold. max_slot_wal_keep_size caps the damage by letting slots be invalidated rather than filling the disk.

Logical replication and wal_level = logical

Streaming replication ships raw WAL — page images, vacuum records, the lot. The standby is required to be identical to the primary, and there is no way to replicate some of the data, much less reshape it on the way. Logical replication solves both. Postgres decodes WAL into a stream of row-level change events (insert, update, delete) and publishes them per table; subscribers replay those events against tables of their choosing.

You opt in by raising wal_level from replica (the default, sufficient for physical) to logical, which makes the decoder include the extra information needed to reconstruct row changes. The cost is a small amount of additional WAL volume and a restart.

A publication on the primary, a subscription on the analytics box

-- on the primary, after `ALTER SYSTEM SET wal_level = logical` + restart
CREATE PUBLICATION app_pub FOR TABLE orders, order_items, customers;

-- on the subscriber
CREATE SUBSCRIPTION app_sub
  CONNECTION 'host=primary.internal user=repl dbname=app'
  PUBLICATION app_pub;

What logical buys you: cross-version replication (PG 14 → PG 16 is fine), partial schemas (replicate only what you need), fan-out (one publication, many subscribers), and zero-downtime major upgrades via a blue-green cutover. What it does not handle, at least not gracefully: DDL changes (you must run them on every side), sequences (the values are not propagated, only the rows that consumed them), very large transactions (decoded into memory before being sent, with PG 14+'s streaming alleviating but not eliminating the cost), and conflict resolution (last-write-wins or break-the-replica are the only built-in options).

Replica identity For an UPDATE or DELETE to logical-replicate, Postgres needs a way to identify the old row on the subscriber. The default is the primary key; tables without one need ALTER TABLE … REPLICA IDENTITY FULL, which logs the full old row. Cheap on narrow tables, painful on wide ones.

Synchronous vs asynchronous commit

By default, COMMIT on the primary returns as soon as the local WAL fsync completes. The standby gets the records moments later, but the primary does not wait. If the primary dies before the standby has caught up, the missing transactions are gone. This is asynchronous replication, and for many workloads — where a few seconds of potential data loss on a hard failover is acceptable — it is the right trade.

Synchronous commit moves that trade. synchronous_commit is a per-session GUC with several levels, each waiting for something more:

off
Don't even wait for the local fsync. Fast, lossy — a crash can lose recent commits. Useful only for bulk-load workloads where you're going to verify and retry.
local
Wait for local fsync. Equivalent to the old fsync = on, synchronous_standby_names = ''. No replica wait.
on (default)
Wait for local fsync; if synchronous_standby_names is set, also wait for the configured replicas to fsync the same WAL.
remote_write
Wait until the standby has received and written (but not yet fsynced) the WAL. Faster than on, weaker durability.
remote_apply
Wait until the standby has actually replayed the WAL and the change is visible to queries against it. Strongest guarantee, highest latency.

Synchronous to one of two standbys

ALTER SYSTEM SET synchronous_commit = on;
ALTER SYSTEM SET synchronous_standby_names = 'ANY 1 (standby_dc1, standby_dc2)';
SELECT pg_reload_conf();

ANY 1 (…) means "any one of the named standbys must ack." FIRST 1 (…) means "the named standbys in priority order; the first one in the list is preferred." The ANY form is what you want for a cross-AZ setup where either AZ ack'ing is fine.

Pitfall

If you list standbys in synchronous_standby_names and all of them go down, every COMMIT on the primary blocks indefinitely. The primary is up and refuses writes — exactly the right answer if you cannot afford to lose data, exactly the wrong answer if you cannot afford downtime. Pick deliberately; synchronous_commit = local per-session is the per-transaction escape hatch when an individual statement does not need the guarantee.

Failover, pg_rewind, replication lag

Failover is the act of promoting a standby to be the new primary because the old one is gone. Mechanically it is one command: pg_ctl promote (or, equivalently, SELECT pg_promote()). The standby stops replaying, ends recovery mode, accepts writes, and begins a new timeline — a new branch in the WAL history that diverges at the moment of promotion.

The harder problem is what to do with the old primary, if it ever comes back. Its WAL diverged from the new primary's at promotion; their LSNs no longer agree. Re-attaching it as a standby naïvely would require a full pg_basebackup — terabytes of copying. pg_rewind exists for exactly this case: it compares the two clusters' WAL, identifies the divergence point, copies only the pages that have changed since, and produces a data directory that can stream from the new primary as a standby.

Resync after failover

# On the old primary, now stopped:
pg_rewind --target-pgdata=/var/lib/postgres/data \
          --source-server='host=new-primary.internal user=replicator' \
          --progress

# Then write standby.signal + primary_conninfo and start it as a standby.
touch /var/lib/postgres/data/standby.signal
pg_ctl -D /var/lib/postgres/data start

Lag is what you watch before, during, and after. pg_stat_replication on the primary has a row per connected standby with the LSNs at each stage (write, flush, replay) and the corresponding lag intervals:

Per-standby lag

SELECT application_name, state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_bytes,
       write_lag, flush_lag, replay_lag
FROM   pg_stat_replication;

A replica with healthy network and adequate hardware should sit at near-zero replay lag. Sustained lag growth means either the standby cannot keep up (CPU or I/O on the replica) or it is being held back by a long read query and hot_standby_feedback behaviour. Both are findable in pg_stat_activity on the standby.

PITR with pg_basebackup + WAL archive

Point-in-time recovery is the discipline that protects you against everything streaming replication does not — application-level data corruption, accidental DROP TABLE, a bug that wrote nonsense for an hour before anybody noticed. The mechanism: take a periodic base backup of the cluster, archive every WAL segment as it is filled, and you can restore to any LSN or timestamp between the backup and the most recent archived segment.

Two settings turn the archive on. archive_mode = on tells the server to invoke a shell command for each completed segment; archive_command is the command. It must copy the file to durable, off-cluster storage and return zero on success — Postgres retries on failure but cannot reclaim WAL until the archive accepts it.

A minimal archive_command

ALTER SYSTEM SET archive_mode = on;
ALTER SYSTEM SET archive_command = 'test ! -f /wal-archive/%f && cp %p /wal-archive/%f';
-- restart required to change archive_mode

The base backup is taken with pg_basebackup, which streams a consistent on-disk snapshot of the cluster while it continues to accept writes. The LSN at the start of the backup is what recovery rewinds to before replaying WAL forward.

Restoring to 14:32 yesterday

# Restore the base backup into a new data directory, then add:
echo "restore_command = 'cp /wal-archive/%f %p'"                > recovery.conf
echo "recovery_target_time = '2026-05-20 14:32:00+00'"          >> recovery.conf
echo "recovery_target_action = 'promote'"                        >> recovery.conf
touch /var/lib/postgres/data/recovery.signal

pg_ctl start
# Postgres replays archived WAL up to the target time and then promotes.

The base backup is straightforward; the WAL archive is also straightforward; the discipline that matters is testing the restore. Backups that have never been restored are not backups. Schedule a periodic restore-into-a-throwaway-cluster job and let it run unattended — it is the only way to know your backup chain works before you need it.

Use a real tool Rolling your own archive_command with cp works for a demo. In production, use pgBackRest or wal-g. Both handle parallel upload, encryption, retention, incremental backups, and — crucially — the verification step you would otherwise forget.

Replication & WAL, in one card

WAL
Append-only log written before any heap change. Crash recovery replays it.
wal_level
replica for streaming, logical for logical replication.
Streaming replication
Physical: standby applies the primary's WAL byte-for-byte. Same Postgres version.
Replication slot
Server-side bookmark that prevents WAL deletion before the standby has consumed it. Watch for unbounded growth.
Hot standby
Streaming standby that also accepts read-only queries.
Logical replication
Decoded row changes per publication/subscription. Cross-version, partial schemas, conflict handling.
synchronous_commit
on: wait for fsync. remote_apply: wait for standby replay. off: fast, lossy.
pg_rewind
Resync a diverged former primary against the new one without a full base backup.
pg_basebackup
One-shot binary copy of the cluster. Foundation of PITR.
PITR
Restore a base backup, replay archived WAL up to a chosen LSN or timestamp.
