Data types, and the shape of nothing

Numbers that lie, timestamps that drift across time zones, text that pretends to be three different types, and a value that compares equal to neither itself nor its absence.

Before any of the harder Postgres mechanics make sense, the type system has to be in your head. Most of the trouble engineers hit in real codebases — silent rounding, surprise time-zone shifts, queries that return nothing because a single column was NULL — comes from misunderstanding what a column actually contains. This chapter is the ground-floor reference.

The type hierarchy at a glance

Postgres ships with a dense built-in type system organised into a handful of families. Most schemas only ever use a small subset, but knowing the families is what lets you pick the right one without thinking about it.

The rest of this chapter focuses on the ones that hurt people: the numerics, the text trio, the two timestamps, arrays and ranges, booleans, UUIDs, enums, and the constant background presence of NULL.

Numerics — numeric, bigint, float8

Three numeric types cover almost every use case in practice, and the choice between them is a three-way trade-off between exact, fast, and compact. Pick wrong and you either lose precision or pay for it in storage and CPU.

bigint
Eight-byte signed integer, range ±9.2 × 1018. The default for counts and identifiers. int (4 bytes, ±2.1 × 109) is fine until it isn't; bigint from day one costs nothing measurable and saves a painful migration later.
numeric(p, s)
Arbitrary-precision decimal. p total digits, s after the point. Exact arithmetic — what you get is what you stored. Slow (software, not hardware) and variably sized on disk. The right type for money, billing, anything that has to add up to the last cent.
double precision (a.k.a. float8)
IEEE 754 binary double. Fast, fixed 8 bytes, and lossy — most decimal fractions cannot be represented exactly. Right for scientific measurements where the inputs are themselves approximations. Wrong for money.

The classic demonstration of why float8 is not a stand-in for decimal:

IEEE 754 rounding vs. exact decimal

SELECT 0.1::float8 + 0.2::float8  AS as_float,
       0.1::numeric + 0.2::numeric AS as_numeric;

Result

as_floatas_numeric
0.300000000000000040.3

The float8 answer is off by one part in 1016 — invisible most of the time, catastrophic when you sum a million of them or compare to a literal 0.3. numeric stores the digits, not a binary approximation, and the answer is exact.

For surrogate primary keys, two spellings produce a self-incrementing bigint. The legacy bigserial macro is shorthand for "create a sequence, set the default to nextval, and own it." The SQL-standard form is bigint GENERATED ALWAYS AS IDENTITY, which is harder to accidentally override and easier to manage explicitly. New code should prefer it; you'll see bigserial everywhere in older schemas.

Pitfall

Never store money in float8 or real. Sums drift, comparisons fail, and audits will not match. Use numeric — and if you want to be loud about it, numeric(12, 2) for cents or numeric(20, 8) for fractional crypto. The CPU cost of decimal arithmetic is irrelevant next to a reconciliation that's three pennies off.

text vs varchar vs char

Three character types, and only one of them is the right default. text is unbounded variable-length and is what almost every column should be.

varchar(n) is identical to text in storage and performance — the same variable-length on-disk format, the same TOAST handling, the same indexing — with one extra check on insert that the value is at most n characters. There is no efficiency reason to prefer it. Use varchar(n) when a real external constraint demands the limit (a fixed-width export format, a downstream column you can't widen), and use text otherwise.

char(n) is the odd one out: it blank-pads every value to exactly n characters on read. This is rarely what anyone wants and it is the source of subtle join misses:

Blank-padding bites a join

CREATE TABLE codes_a (code char(5));
CREATE TABLE codes_b (code text);
INSERT INTO codes_a VALUES ('AB');     -- stored and returned as 'AB   '
INSERT INTO codes_b VALUES ('AB');

SELECT length(a.code), length(b.code)
FROM codes_a a JOIN codes_b b ON a.code = b.code;

Result (the join works by a Postgres-specific quirk, but the lengths disagree)

lengthlength
52

Cross to any other system — an application string-compare, a CSV export, a different database — and the trailing spaces stop being invisible. Almost every char(n) in the wild is a mistake inherited from a port of fixed-width COBOL or DB2 code.

Large values are handled transparently. When a row would overflow a single 8 KB page, Postgres compresses and slices the wide columns into a side relation called TOAST. You never see this from SQL — a megabyte of text reads and writes like any other value — but it explains why a single column can hold a gigabyte without anything in your schema looking different.

Collation Every text column has a collation that controls sorting and pattern matching. COLLATE "en_US.utf8" sorts naturally ("apple" < "Banana"); COLLATE "C" sorts by raw byte order ("Banana" < "apple") and is what you want for an indexed column you compare with = or LIKE 'prefix%'. Mismatched collations across columns force a re-encode and can defeat index usage.

timestamptz vs timestamp

This is the highest-value section in the chapter. Pick wrong and your application silently misreports times for every user not in the database server's local zone; pick right and the problem disappears forever.

timestamptz (timestamp with time zone) stores a UTC instant. On insert, the literal is interpreted in the session's TIMEZONE and converted to UTC; on read, the UTC instant is converted back to the session's zone for display. The column itself stores no zone — just 8 bytes counting microseconds from the Postgres epoch. The name is misleading: there is no zone in the value.

timestamp (timestamp without time zone) stores a wall-clock string of digits with no zone attached and no conversion performed. '2026-05-21 14:00' means whatever you decide it means; the database stores the digits and hands them back unchanged. This is almost always wrong, and the few cases where it is right (a calendar event that should fire at 09:00 local wherever the user is, regardless of zone) are usually better modelled as (local_timestamp, zone_name).

The same INSERT in two zones

CREATE TABLE ev (kind text, tz timestamptz, no_tz timestamp);

SET TIMEZONE = 'UTC';
INSERT INTO ev VALUES ('utc-write', '2026-05-21 14:00', '2026-05-21 14:00');

SET TIMEZONE = 'America/New_York';   -- UTC-4 on this date
INSERT INTO ev VALUES ('ny-write',  '2026-05-21 14:00', '2026-05-21 14:00');

SELECT * FROM ev;

Result (session still America/New_York)

kindtzno_tz
utc-write2026-05-21 10:00:00-042026-05-21 14:00:00
ny-write 2026-05-21 14:00:00-042026-05-21 14:00:00

The two timestamptz rows store different UTC instants (14:00 UTC vs 18:00 UTC) because the input was interpreted in different zones; the display zone is the session's. The two timestamp rows are byte-for-byte identical despite having been written under different zones — the database simply did not care. That is the bug.

Three "now" functions, three subtly different meanings:

now() / transaction_timestamp()
The moment the current transaction began. Constant for the life of the transaction — call it ten times, get the same answer ten times.
statement_timestamp()
The moment the current statement began. Advances between statements in the same transaction.
clock_timestamp()
The actual wall clock, read fresh each call. The only one that moves inside a single statement. Useful for measuring time inside a long query; never use it as a default for "when did this row land."
Pitfall

Comparing a timestamptz column to a bare string literal like '2026-05-21 00:00' implicitly casts the literal using the session's TIMEZONE. The same query run from a server in UTC and an analyst's laptop in Lisbon returns different rows. Either set TIMEZONE explicitly in your session, or write zone-qualified literals: '2026-05-21 00:00 UTC'::timestamptz.

boolean

One byte on disk, three possible values: true, false, and NULL. The third one is what trips people up — every nullable boolean column is a three-valued column, and ordinary boolean operators propagate the unknown.

Two queries that look equivalent and are not:

Boolean filters with NULLs in the column

CREATE TABLE users (id int, active boolean);
INSERT INTO users VALUES (1, true), (2, false), (3, NULL);

SELECT count(*) FILTER (WHERE NOT active)      AS not_active,
       count(*) FILTER (WHERE active IS NOT TRUE) AS not_true,
       count(*) FILTER (WHERE active = FALSE)  AS eq_false
FROM users;

Result

not_activenot_trueeq_false
121

NOT active and active = FALSE both quietly drop the NULL row, because the predicate evaluates to NULL and WHERE treats NULL as false. active IS NOT TRUE is the predicate that catches both false and unknown — usually what the question "who is not active?" actually means. Make the column NOT NULL DEFAULT FALSE if you can; if you can't, write your predicates with IS [NOT] TRUE/FALSE and not bare boolean operators.

uuid

A fixed 16-byte identifier, displayed as the familiar 8-4-4-4-12 hex string. Half the byte cost of storing the same value as text, and the right type any time you need an identifier that can be generated by a client without coordinating with the database.

Since Postgres 13, version-4 UUIDs are a one-function call in core — no extension required:

UUID column with a built-in default

CREATE TABLE sessions (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    bigint NOT NULL,
  started_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO sessions (user_id) VALUES (42) RETURNING id;

Result

id
9e2c5f7a-1b3d-4e6f-8a2b-7c1d3e5f9a04

The trade-off against bigint identity is twofold. UUIDs are twice the size — measurable in indexes and join keys on hot tables — and version-4 values are random, so every insert lands in a different B-tree page. That spreads write traffic across the index instead of concentrating it at the tail, which is bad for cache locality and bloat. For a high-throughput write workload on a single database, an identity bigint is cheaper. For distributed systems, opaque external IDs, or anywhere the client must mint the ID before talking to the database, the UUID is correct.

UUIDv7 The fix for the locality problem is UUIDv7 — 128 bits, but with a millisecond timestamp in the high bits so values are roughly time-ordered. Available today via extensions (pg_uuidv7) and on the roadmap for core. If you're starting a new schema, it's worth a look.

Arrays and ranges

Two collection types that share a syntax family and almost nothing else. Arrays are first-class and frequently misused. Ranges are powerful, underused, and the cleanest way to model intervals.

Arrays

Any type can be made into an array by suffixing []. Arrays support equality, containment (@>), overlap (&&), and a GIN index for O(log n) lookups by element. They're genuinely useful for short, append-only lists where the order matters and you'll never need to join — tag lists for full-text search, ordered path components, the small fixed vector of a denormalised cache.

Array column with a GIN index

CREATE TABLE posts (
  id   bigserial PRIMARY KEY,
  tags text[] NOT NULL DEFAULT '{}'
);

CREATE INDEX posts_tags_gin ON posts USING gin (tags);

SELECT id FROM posts WHERE tags @> ARRAY['postgres', 'mvcc'];
Pitfall

An array column is not a relationship. Storing tag_ids int[] instead of a post_tags(post_id, tag_id) join table loses every benefit a join table gives you: foreign-key enforcement on each ID, ordinary B-tree indexes for "all posts with tag X", efficient many-to-many joins, and the ability to add columns to the relationship itself (when the tag was added, by whom). If the application ever needs to ask "show me all posts tagged X, joined with the tag's metadata" the array model collapses.

Ranges

A range is a single column holding a lower and upper bound over an orderable type, with explicit inclusivity. Built-in range types include int4range, numrange, tsrange, tstzrange, and daterange. They support containment (@>), overlap (&&), adjacency (-|-), and — crucially — pair with EXCLUDE constraints to enforce non-overlap at the database level.

Reservations that cannot overlap

CREATE EXTENSION IF NOT EXISTS btree_gist;  -- so '=' on room_id works in GiST

CREATE TABLE bookings (
  id      bigserial PRIMARY KEY,
  room_id int NOT NULL,
  during  tstzrange NOT NULL,
  EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

INSERT INTO bookings (room_id, during)
VALUES (1, '[2026-05-21 09:00+00, 2026-05-21 10:00+00)');

INSERT INTO bookings (room_id, during)
VALUES (1, '[2026-05-21 09:30+00, 2026-05-21 10:30+00)');
-- ERROR:  conflicting key value violates exclusion constraint
--         "bookings_room_id_during_excl"

The constraint is enforced by the database, atomically, without a trigger and without a race. The full EXCLUDE story lives in Schema design & constraints.

Enums and composite types

An ENUM is a closed set of named string values stored on disk as a 4-byte oid. Cheap, ordered (by declaration order, not alphabetical), and statically typed — assigning a string outside the set is a parse error, not a runtime check.

Enum for a fixed status column

CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');

CREATE TABLE orders (
  id     bigserial PRIMARY KEY,
  status order_status NOT NULL DEFAULT 'pending'
);

SELECT * FROM orders WHERE status < 'shipped';  -- uses declaration order

The catch is evolution. ALTER TYPE … ADD VALUE works (and since PG 12 can be run outside a transaction block), but you cannot remove a value, you cannot reorder, and renaming requires ALTER TYPE … RENAME VALUE. For a set that changes monthly, a text column with a CHECK (status IN (…)) constraint — or a statuses lookup table with an FK — is more flexible. For a set that's stable for years (US states, ISO currency, the four sides of a coin), an enum is the right choice and reads beautifully in queries.

Composite types are the other half of CREATE TYPE: a named record shape, useful for function return values and occasionally for columns that genuinely model a tuple (a postal address, an RGB colour). They're rare in application schemas and common in extension code.

NULL, three-valued logic, IS DISTINCT FROM

The conceptual heart of the chapter. NULL is not a value; it is the absence of one. The slogan is "unknown." Every comparison involving NULL evaluates to NULL — not true, not false, unknown — and WHERE, CASE, and HAVING all treat NULL as if it were false. From this one rule, all the surprises follow.

Why = NULL never matches

CREATE TABLE t (id int, val int);
INSERT INTO t VALUES (1, 10), (2, NULL), (3, 20);

SELECT * FROM t WHERE val = NULL;       -- returns zero rows
SELECT * FROM t WHERE val IS NULL;      -- returns the row with id=2
SELECT * FROM t WHERE val IS NOT DISTINCT FROM NULL;  -- same: id=2

val = NULL evaluates to NULL for every row including the one where val actually is null; WHERE NULL filters that row out. IS NULL is the only equality test that treats two nulls as equal. IS DISTINCT FROM is its sibling: a null-safe inequality that returns true when one side is null and the other isn't, and false when both are null. It is the equality you actually wanted across nullable columns:

Comparing nullable columns sensibly

-- "did this row change?" against an audit table
SELECT *
FROM   current c
JOIN   previous p USING (id)
WHERE  c.email IS DISTINCT FROM p.email
   OR  c.phone IS DISTINCT FROM p.phone;

Three more places NULL behaviour bites:

NOT IN (subquery)
If the subquery ever yields a single NULL, the entire NOT IN evaluates to NULL for every outer row, and the outer query returns zero rows. NOT EXISTS is the safe rewrite.
Aggregates
COUNT(*) counts rows; COUNT(col) counts non-null values of col. SUM, AVG, MIN, MAX all skip nulls. AVG over an all-null group returns NULL, not zero.
UNIQUE constraints
By default, two NULLs are not considered equal, so a UNIQUE column happily accepts many rows with NULL in it. UNIQUE NULLS NOT DISTINCT (PG 15+) flips this. See Schema design & constraints.
Warning

SELECT * FROM orders WHERE id NOT IN (SELECT order_id FROM shipments) looks reasonable. If a single row in shipments.order_id is NULL, the query silently returns nothing — every order looks "not shipped" because id NOT IN (…, NULL, …) can never be proven true. Use NOT EXISTS (SELECT 1 FROM shipments s WHERE s.order_id = orders.id) instead, which has the obvious semantics.

json vs jsonb — a pointer

Two JSON types, and one of them is the right default. jsonb stores a parsed, decomposed binary representation: insert is slightly more expensive (validation + decompose), every read is faster, and the value supports operator-class indexing with GIN. json stores the original text verbatim, preserving whitespace and key order; every operation re-parses. Use json only when you genuinely need to round-trip the bytes a client sent you. Otherwise, jsonb. The full chapter lives at JSONB.

Domains and custom types

A domain is a named alias for an existing type, optionally wrapped in a CHECK constraint and a default. It lets you give a column shape a name — "an email," "a positive amount," "a US ZIP code" — and reuse it across tables with the validation applied automatically.

A domain for email addresses

CREATE DOMAIN email AS text
  CHECK (VALUE ~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]+$');

CREATE TABLE accounts (
  id       bigserial PRIMARY KEY,
  primary_email   email NOT NULL,
  recovery_email  email
);

INSERT INTO accounts (primary_email) VALUES ('not-an-email');
-- ERROR:  value for domain email violates check constraint "email_check"
-- SQLSTATE: 23514

The same regex repeated across three tables is three places a typo can land. The domain is one place, one definition, one rule. Changing the rule (ALTER DOMAIN … ADD CONSTRAINT … NOT VALID) revalidates only the rows that need it.

Domains cannot enforce inter-column rules — they see one value at a time, not the row — so "ends_at must be after starts_at" still belongs in a table-level CHECK. And a domain does not give you a new type for the purposes of function overloading; it is the underlying type with a label. Even so: under-used, low-cost, and clarifying when applied to a column shape you find yourself defining more than once.

In practice Domains show up rarely in application schemas and constantly in well-built extensions. They are one of the easiest wins for a schema you intend to live with for years.

Data types, in one card

numeric
Exact arbitrary-precision. Use for money.
float8
IEEE 754 double. Fast, lossy. Never for money.
bigint
The right default integer. Prefer GENERATED ALWAYS AS IDENTITY over bigserial in new code.
text
The right default. varchar(n) only when an external system imposes the limit. char(n) almost never.
timestamptz
UTC instant. The right default for "when did this happen."
timestamp
Wall-clock with no zone. Almost always wrong.
boolean
Three-valued. Prefer NOT NULL DEFAULT FALSE; write IS NOT TRUE when nulls are possible.
uuid
16 bytes, gen_random_uuid() built in since PG 13. Worse index locality than identity bigints; UUIDv7 is the fix.
NULL
"Unknown." NULL = NULL is NULL, not true.
IS DISTINCT FROM
The equality you actually wanted across nullable columns.
Arrays
int[], text[]. GIN-indexable. Don't model relations with them.
Ranges
tstzrange, int4range. Pair with EXCLUDE for non-overlap constraints.
ENUM
Closed sets, cheap and ordered. Hard to evolve — use CHECK or a lookup table if values churn.
jsonb
The right default for semi-structured data. json only for byte-exact round-trips.
Domains
Named, reusable column shapes with a built-in CHECK. Under-used.
